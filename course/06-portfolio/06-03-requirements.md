# 6-3 要件定義と画面設計

> 🎯 **このレッスンのゴール**
> - 「何を作るか」を、作り始める前に言葉と図で決められる
> - 機能要件・画面遷移・データ設計を、初学者レベルで一通り書ける
> - 行き当たりばったりの開発から卒業する

所要 150分 / 難度 🟡 ／ 🏁 成果物：要件定義書

---

## 📖 なぜ「作る前に決める」のか

初学者がオリジナルアプリで挫折する最大の原因は、**作りながら考えるから**です。

- 途中で「あれも要る、これも要る」と膨らむ → 終わらない
- 画面を作ってから「このデータどこに保存？」と気づく → 作り直し
- ゴールが曖昧 → どこまでやれば完成か分からない

これを防ぐのが**要件定義**（何を作るかを先に決める）と**設計**（どう作るかを先に描く）です。

> 🧠 **料理でいえば、レシピと買い物リスト**。
> 作りながら足りない材料に気づいて何度もスーパーに走る人と、
> 先にレシピを見て買い物を済ませる人。どちらが早く・確実に完成するかは明らかです。

第5部の総合演習では、この工程を「フリマアプリ」で体験しました。今回はそれを**自分の言葉で
再現できる**ようにします。

---

## ✍️ 手を動かす① ─ 要件定義：機能を洗い出す

まず「このアプリで、誰が、何をできるか」を箇条書きにします。主語は**ユーザー**。

例（ToDo共有アプリの場合）：

```
【ゲスト（未ログイン）ができること】
- トップページを見る
- 新規登録・ログインする

【ログインユーザーができること】
- タスクを作成・編集・削除する
- タスクを完了にする
- 自分のタスク一覧を見る
- タスクを他ユーザーと共有する
```

次に、それぞれに **MoSCoW** で優先度を付けます。

| 優先度 | 意味 | 例 |
| --- | --- | --- |
| Must（必須） | これが無いと成立しない | タスクのCRUD、ログイン |
| Should（推奨） | あると良い | 完了フラグ、期限 |
| Could（任意） | 余裕があれば | 共有、タグ |
| Won't（今回やらない） | あえて外す | 通知メール、スマホアプリ |

> 💡 **Won't（やらないこと）を決めるのが一番大事**。
> 「今回はここまで」と線を引かないと、永遠に完成しません。まずは Must だけで
> **動くもの（MVP）**を完成させる、が鉄則です。

## ✍️ 手を動かす② ─ 画面遷移図を描く

「どの画面から、どの画面に移動できるか」を矢印でつなぎます。手書きでもOK。

```
[トップ/一覧]
   ├─→ [ログイン] ─→ [ログイン後トップ]
   ├─→ [新規登録] ─→ [ログイン後トップ]
   └─→ [タスク詳細]
            ├─→ [編集画面] ─→ [タスク詳細]
            └─(削除)→ [一覧]
```

これを描くと、**必要な画面（＝ルート）の一覧**が自然に見えてきます。
第5部のルート設計（5-3）は、この図から作れます。

| 画面 | URL | メソッド | ログイン要否 |
| --- | --- | --- | --- |
| 一覧 | `/tasks` | GET | 不要 |
| 詳細 | `/tasks/{id}` | GET | 不要 |
| 作成フォーム | `/tasks/create` | GET | 必要 |
| 作成処理 | `/tasks` | POST | 必要 |
| 編集フォーム | `/tasks/{id}/edit` | GET | 必要（本人） |
| 更新処理 | `/tasks/{id}` | PUT | 必要（本人） |
| 削除処理 | `/tasks/{id}` | DELETE | 必要（本人） |

## ✍️ 手を動かす③ ─ データ設計（ER図）

「どんなデータを、どのテーブルに持つか」を決めます。第4部の正規化・リレーションの出番。

```
users
  - id
  - name
  - email
  - password

tasks
  - id
  - user_id      (→ users.id)   誰のタスクか
  - title
  - body
  - is_done      完了フラグ
  - due_date     期限（任意 = NULL可）
  - created_at / updated_at
```

チェックすること（第4部の知識）：

- [ ] 同じ情報を複数の場所に重複して持っていないか（正規化）
- [ ] テーブル同士のつながりに**外部キー**があるか
- [ ] NULLを許す列は妥当か
- [ ] よく検索する列にインデックスが要らないか

> 💡 このER図が決まれば、第5部の**マイグレーション（5-6）とモデル（5-7, 5-8）**が
> ほぼ機械的に書けます。設計に時間をかけるほど、実装は速くなります。

---

## ✍️ 手を動かす④ ─ 要件定義書にまとめる

上の①〜③を1つの文書（`docs/requirements.md` など）にまとめます。構成例：

```markdown
# ○○アプリ 要件定義書

## 1. 概要
（1〜2文で「何のアプリか」）

## 2. 想定ユーザー / 解決する課題
（誰の、どんな困りごとを解決するか）

## 3. 機能一覧（MoSCoW）
（Must / Should / Could / Won't の表）

## 4. 画面遷移
（画面遷移図）

## 5. 画面ごとの仕様
（各画面のURL・メソッド・ログイン要否の表）

## 6. データ設計（ER図）
（テーブルと列、リレーション）

## 7. 今回のスコープ（MVP）
（最初に完成させる範囲を明記）
```

> 🧠 **この文書は、そのままポートフォリオの一部**になります。
> 「設計してから作れる人」であることの証明です。READMEからリンクしておきましょう。

---

## ⚠️ つまずきポイントまとめ

| 症状 | 原因 | 対処 |
| --- | --- | --- |
| 機能が無限に増える | Won't を決めていない | MVPの線を引く。Must だけ先に |
| 作ってからデータ設計に気づく | ER図を後回しにした | 実装前にER図を確定 |
| 画面が思ったより多くて挫折 | スコープが広すぎ | Should/Could を後回しに |
| 完成が分からない | ゴールが曖昧 | 「MVPが動いたら第一段階完成」と定義 |

## 🤖 AIに聞いてみよう

要件定義・設計は、AIが「壁打ち相手」として非常に有用です（5-15の応用）。

### 使えるプロンプト例

```
○○を解決するWebアプリを作りたいです。まず要件定義を手伝ってください。
- 想定ユーザー: （書く）
- やりたいこと: （箇条書き）
次を提案してください：
1. 機能一覧を MoSCoW で分類（特に「今回やらないこと」を明確に）
2. 必要な画面と画面遷移
3. 必要なテーブルとリレーション（ER図の案）
初学者が Laravel で1〜2週間で作れる MVP の範囲も提案してください。
```

### 🔍 AIの答えを疑うチェックリスト

- [ ] MVPの範囲が**現実的**か（初学者が完成させられる量か）
- [ ] 「やらないこと（Won't）」がちゃんと提案されているか
- [ ] ER図案が第4部の観点（正規化・外部キー）で妥当か
- [ ] 画面と機能・データが**一貫**しているか（画面にあるのにデータが無い、等が無いか）
- [ ] あなた自身が「なぜこの設計か」を説明できるか

> 🧠 AIは機能をたくさん提案してくれますが、**削る判断は人間の仕事**。
> 「全部入り」の設計は完成しません。AIの案から Must を選び取る力を鍛えましょう。

## 🔧 やってみよう（演習）

1. 作りたいアプリのアイデアを1つ決める（次の6-4で企画として深めます）
2. 機能を洗い出し、MoSCoW で分類する（Won't を必ず書く）
3. 画面遷移図を描く（手書き可）
4. 画面ごとの仕様表（URL・メソッド・ログイン要否）を作る
5. ER図を描く（第4部のチェックリストで検算）
6. これらを `docs/requirements.md` にまとめる
