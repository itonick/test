# 6-2 読まれる README の書き方

> 🎯 **このレッスンのゴール**
> - リポジトリを開いた人が「何のアプリか・どう動かすか」を30秒で理解できるREADMEを書ける
> - 採用担当・レビュアーが知りたい情報を、順番に並べられる
> - フリマアプリのREADMEを完成させる

所要 90分 / 難度 🟢 ／ 🏁 成果物：README

---

## 📖 README は「作品の顔」

GitHubのリポジトリを開くと、最初に大きく表示されるのが `README.md` です。
採用担当やレビュアーは、まずここを読みます。**コードより先に読まれる**のがREADME。

- READMEが無い／雑 → 「動かし方が分からない」「熱意が伝わらない」
- READMEが丁寧 → 「この人はちゃんと伝える力がある」

コードの実力が同じなら、READMEの差がそのまま評価の差になります。

> 🧠 **READMEはドキュメントであり、プレゼンでもある**。
> 「自分がこのアプリを知らない人だったら、何が知りたいか」を想像して書きます。

---

## 📖 README に載せるべき項目（この順で）

上から読んで自然に理解できる順番です。

1. **アプリ名 + 一言説明**（何のアプリか）
2. **スクリーンショット / デモ**（見た目・動くURLがあれば最強）
3. **主な機能**（何ができるか、箇条書き）
4. **使用技術**（言語・フレームワーク・DB）
5. **セットアップ手順**（他人が自分のPCで動かせるように）
6. **工夫した点 / こだわり**（← ここが差別化。後述）
7. **今後の課題**（伸びしろを見せる）

---

## ✍️ 手を動かす① ─ README のひな形（コピペ用）

`README.md` をリポジトリ直下に作り、次を土台にします。

```markdown
# フリマアプリ（Flea Market App）

不要品を出品・購入できる、シンプルなフリマアプリです。
Laravel の学習の総まとめとして、認証・認可・決済状態管理・テストまでを実装しました。

## 📸 スクリーンショット

![商品一覧](docs/screenshot-index.png)
![商品詳細](docs/screenshot-show.png)

## ✨ 主な機能

- ユーザー登録・ログイン（Laravel Breeze）
- 商品の出品（画像アップロード対応）
- 商品一覧・詳細・キーワード検索・ページネーション
- 商品の購入（購入済みは他ユーザーが購入不可）
- マイページ（出品履歴・購入履歴）
- 出品の編集・削除（本人のみ）

## 🛠 使用技術

- PHP 8.x / Laravel 11
- MySQL 8.x
- Blade / Tailwind CSS
- PHPUnit（機能テスト）

## 🚀 セットアップ

\`\`\`bash
git clone https://github.com/あなた/flea-market.git
cd flea-market

composer install
npm install && npm run build

cp .env.example .env
php artisan key:generate
# .env にDB接続情報を設定

php artisan migrate --seed
php artisan storage:link
php artisan serve
\`\`\`

http://localhost:8000 にアクセス。

## 💡 工夫した点

- **二重販売の防止**：購入処理をトランザクション＋行ロック（\`lockForUpdate\`）で保護し、
  同時アクセスでも1商品が2人に売れないようにした。
- **なりすまし対策**：\`user_id\` はフォームから受け取らず、ログインユーザーから設定。
  出品の編集・削除はポリシーで本人のみに制限。
- **N+1問題への対応**：一覧・履歴で \`with()\` を使い、発行クエリ数を確認しながら実装。

## 📝 今後の課題

- カテゴリ・タグ機能の追加
- 商品へのコメント / レビュー機能
- 決済サービスとの連携

## 🧑‍💻 作者

- 名前 / GitHub / (任意で) ポートフォリオサイト
```

> 💡 バッククォート3つ（```）で囲むと**コードブロック**になります。上の例では
> 表示のために `\`\`\`` とエスケープしていますが、実際のREADMEでは普通の ``` を使います。

---

## ✍️ 手を動かす② ─ スクリーンショットを入れる

文字だけのREADMEより、**画像が1枚ある**だけで印象が激変します。

1. アプリを動かして、主要画面のスクショを撮る
2. リポジトリに `docs/` フォルダを作り、画像を置く
3. READMEに `![説明](docs/ファイル名.png)` で埋め込む

> 💡 動くURL（6-6でデプロイ）があれば、READMEの先頭に
> `## 🔗 デモ: https://...` を置くのが最強。「実際に触れる」に勝るアピールはありません。

---

## ✍️ 手を動かす③ ─ 「工夫した点」で差をつける

ここが**他の学習者と差がつく決定的なパート**です。
機能一覧は誰でも書けます。でも「なぜそう作ったか」は、理解している人しか書けません。

### ❌ 弱い書き方

> 購入機能を実装しました。

### ✅ 強い書き方

> **二重販売の防止**：単純に status を確認して更新するだけだと、2人が同時に購入した際に
> レースコンディションで両方売れてしまう。これを防ぐため、購入処理を
> `DB::transaction` で囲み、`lockForUpdate()` で対象商品に行ロックを取ってから
> 状態を確認・更新するようにした。

この一文で、採用担当は「トランザクション・排他制御・レースコンディションを理解している」
と分かります。**第4部・第5部で学んだことを、言葉で説明できる**のが強み。

> 🧠 **「工夫した点」は、この教材で学んだ観点の見せ場**。
> N+1対策、mass assignment対策、認可、バリデーション、テスト……
> あなたが「なぜそうしたか」を語れる場所です。3つは書きましょう。

---

## ⚠️ つまずきポイントまとめ

| 症状 | 原因 | 対処 |
| --- | --- | --- |
| セットアップ手順通りに動かない | 自分の環境の前提が抜けている | 別フォルダにcloneして手順を実際に試す |
| 画像が表示されない | パスが間違い / 画像を push していない | 相対パス確認、`git add docs/` |
| 何を書けばいいか分からない | 読み手を想像していない | 「知らない人が動かすには？」から逆算 |
| `.env` の値をREADMEに書いた | 機密の混入 | `.env.example` を案内し、実値は書かない |

> 🔒 READMEに**実際のパスワードやAPIキーを書かない**こと。
> 「`.env` にDB情報を設定」と手順だけ示し、値は各自に入れてもらいます（6-1・第4部の延長）。

## 🤖 AIに聞いてみよう

READMEはAIが得意な領域。ただし**中身の正確さ**はあなたが担保します。

### 使えるプロンプト例

```
次の情報から、GitHub用のREADME.md を書いてください。
- アプリ名: フリマアプリ
- 技術: Laravel 11, MySQL, Blade
- 機能: （箇条書きで渡す）
- 工夫した点: 二重販売防止（トランザクション+ロック）, なりすまし対策, N+1対策
セットアップ手順と「今後の課題」も含めてください。
```

### 🔍 AIの答えを疑うチェックリスト

- [ ] セットアップ手順が**実際に自分のアプリで動く**内容か（コマンドを実際に試す）
- [ ] 使っていない技術を「使った」と書いていないか（**嘘は書かない**）
- [ ] 「工夫した点」が、自分が**説明できる**内容になっているか（面接で聞かれる）
- [ ] `.env` の実値など**機密**が紛れ込んでいないか
- [ ] 誇張していないか（「エンタープライズ級」など実態と合わない表現）

> ⚠️ **READMEに書いたことは、面接で全部聞かれる前提**で。
> AIが盛った表現をそのまま載せて、中身を説明できないと逆効果です。
> 「自分の言葉で説明できること」だけを書きましょう。

## 🔧 やってみよう（演習）

1. フリマアプリの `README.md` を、上のひな形をもとに作成
2. アプリを動かしてスクショを2枚撮り、`docs/` に置いて埋め込む
3. 「工夫した点」を、**この教材で学んだ観点**から3つ、自分の言葉で書く
4. 別のフォルダにリポジトリを `clone` し、READMEのセットアップ手順**だけ**を見て
   アプリが起動できるか試す（動かなければ手順を直す）
5. コミットして push し、GitHub上で見栄えを確認

## ✅ 章末チェック

1. READMEが「コードより先に読まれる」のはなぜか。
2. READMEに載せるべき項目を、順番に5つ以上挙げよ。
3. 「工夫した点」で差がつく理由と、書くときの注意（面接との関係）を述べよ。
4. AIにREADMEを書かせるとき、絶対に確認すべきことは？

> 次回は、アプリを作る**前**の工程 ── 要件定義と画面設計に戻ります。
> 「何を作るか」を決める力が、オリジナルアプリ制作の土台になります。
