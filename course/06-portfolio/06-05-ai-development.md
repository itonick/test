# 6-5 🤖 AIと進める個人開発の進め方

> 🎯 **このレッスンのゴール**
> - 企画から完成まで、AIを相棒にした開発サイクルを回せる
> - 「AIに任せる所」と「自分がやる所」を切り分けられる
> - AIを使って開発しても、自分の実力として説明できる状態を保てる

所要 120分 / 難度 🟡

---

## 📖 この教材の集大成 ── AIとの正しい付き合い方

第0部で「AIを疑え」と言い、各部で「AIのコードをチェックしろ」と練習し、
5-15・6-4で「AIと設計を相談する」を学びました。
このレッスンは、それらを**一本の開発サイクル**につなげます。

大前提を、もう一度確認します。

> 🧠 **AIは、あなたを加速する道具。あなたの代わりに責任を負う存在ではない。**
> AIが書いたコードでも、リポジトリに commit した瞬間、それは**あなたのコード**です。
> バグも、セキュリティ穴も、あなたの責任。だから**理解できないコードは commit しない**。

---

## 📖 AIと進める開発サイクル（1機能ずつ回す）

大きく作ろうとせず、**1機能を小さく回す**のが挫折しないコツです。

```
① 設計する（何を作るか／どのテーブル・ルート）      ← 自分（AIに相談可）
② AIにたたき台を書かせる                            ← AI
③ 読んで理解する（分からない所は説明させる）        ← 自分
④ 自分の環境で動かす                                ← 自分
⑤ レビューする（各部のチェックリストで採点）        ← 自分
⑥ 直す／AIに直させる                                ← 自分 + AI
⑦ テストを書く／通す                                ← 自分（AIに補助）
⑧ commit する                                       ← 自分
→ 次の機能へ ①に戻る
```

ポイントは、**③④⑤⑧が「自分」**であること。ここを飛ばすと、
「動くけど自分では説明できないアプリ」ができ、面接で崩れます。

---

## ✍️ 手を動かす① ─ AIに「たたき台」を書かせる（②）

機能単位で、**文脈を渡して**依頼します。丸投げしない。

### 良い依頼の例

```
Laravel 11 で読書記録アプリを作っています。今から「本の登録機能」を実装します。

【前提】
- books テーブル: id, user_id, title, author, status(未読/読了), created_at
- Book モデルは作成済み、User と hasMany/belongsTo で関連済み
- 認証は Breeze 導入済み

【お願い】
- 本を登録するフォームリクエスト、コントローラの store、Blade フォームを書いてください
- user_id はログインユーザーから設定（フォームからは受け取らない）
- バリデーション: title必須100文字、author必須、status は 未読/読了 のいずれか
```

前提（テーブル・既存コード）を渡すと、あなたのアプリに**噛み合うコード**が返ります。

---

## ✍️ 手を動かす② ─ 読んで理解する（③）

返ってきたコードを、**上から下まで読む**。分からない行があったら、こう聞きます。

```
このコードの ○行目の `$request->user()->books()->create(...)` は何をしていますか？
なぜ Book::create() ではなく this を使うのですか？初心者向けに説明してください。
```

> 🧠 **「なぜこう書くのか」を1行ずつ説明できる**状態を目指す。
> これができていれば、面接で「このコードの意図は？」と聞かれても答えられます。
> 逆に、説明できない行が残っているなら、まだ commit してはいけません。

> 🆘 **ここで詰まったら**（AIのコードが動くけれど、理解が追いつかない）
> - **やること**：**わからない行を、そのままAIに質問する**。「この行は何をしていますか」「この行を消すと何が起きますか」と1行ずつ潰す。それでも腹落ちしなければ、その機能を**もっと小さく作り直させる**
> - **鉄則**：説明できないコードは commit しない。動いても、後で自分が直せず・面接で崩れます（この教材が最初から言い続けていること）
> - **こう聞く**：
>   「このコードの ○行目を、初心者向けに1行ずつ説明してください。特に、なぜこの書き方が必要なのかを教えてください」

---

## ✍️ 手を動かす③ ─ レビューする（⑤）

この教材で作ったチェックリストが、そのままレビュー基準になります。

| 観点 | チェック | 学んだ場所 |
| --- | --- | --- |
| mass assignment | `$fillable` に危険な列が無いか | 5-7 |
| なりすまし | `user_id` をフォームから受けていないか | 5-10 |
| 認可 | 本人だけの操作に `authorize` があるか | 5-11 |
| N+1 | 一覧に `with()` があるか | 5-8 |
| バリデーション | 入力チェックが十分か | 5-9 |
| SQLインジェクション | 生SQLに入力を直接埋めていないか | 第4部 |
| XSS | Blade で `{!! !!}` を安易に使っていないか | 5-5 |
| アップロード | 形式・サイズ制限があるか | 5-12 |

> 💡 このリストを `docs/review-checklist.md` にして、機能を作るたびに見返すと、
> 抜け漏れが激減します。これは**あなたの武器**です。

---

## ✍️ 手を動かす④ ─ エラーはAIと解決する（⑥）

エラーが出たら、**メッセージ全文と、関係するコード**を渡します。

```
Laravel でこのエラーが出ました。原因と対処を教えてください。
【エラー】
（エラーメッセージ全文を貼る）
【関係するコード】
（コントローラ or Blade の該当部分を貼る）
【やろうとしたこと】
本の登録フォームを送信したところ発生しました。
```

第0部の付録「エラー辞典」の姿勢そのままです。**症状だけでなく文脈を渡す**と、的確な答えが返ります。

> ⚠️ AIの修正案も**そのまま貼らず**、なぜ直るのかを理解してから適用。
> 「動いた」で終わると、同じエラーに次も対処できません。

---

## ✍️ 手を動かす⑤ ─ テストで品質を固定する（⑦）

機能ができたら、AIにテストを書かせて品質を固定します（5-14）。

```
この BookController の store に対する Feature テストを書いてください。
- ログインユーザーは本を登録でき、booksテーブルに user_id 付きで保存される
- 未ログインでは登録できない（/login にリダイレクト）
- title が空だと登録できない（バリデーションエラー）
RefreshDatabase とファクトリを使ってください。
```

テストが通れば、その機能は「壊れていないことが証明された」状態になります。
以降、AIに別機能を追加させても、`php artisan test` で回帰を検知できます。

## 📖 AIに任せてよい所 / 自分がやるべき所

| AIに任せてよい（得意） | 自分がやるべき（責任） |
| --- | --- |
| ボイラープレート（定型コード）の生成 | 何を作るかの決定（企画・設計） |
| Blade の見た目・CSS | セキュリティ・認可の最終判断 |
| エラーメッセージの解読 | コードを理解すること |
| テストのたたき台 | 「本当に必要か」の取捨選択 |
| リファクタリングの提案 | commit する判断 |
| ドキュメントの下書き | 説明できる状態の維持 |

> 🧠 境界線はシンプル：**「間違っていたら誰が責任を取るか」**。
> 責任があなたに来る所（設計・セキュリティ・commit）は、AIに決めさせない。

---

## ⚠️ AI開発でやりがちな失敗

| 失敗 | 何が起きるか | 対策 |
| --- | --- | --- |
| 理解せず大量にコピペ | 説明できないアプリ／後で直せない | 1機能ずつ、理解してから進む |
| 一度に大きく作らせる | どこが原因か分からなくなる | 小さく回す（1機能ずつ） |
| エラー解決を鵜呑み | 同じエラーに再び詰まる | 「なぜ直るか」を理解する |
| セキュリティをAI任せ | 認可漏れ・情報漏洩 | チェックリストで自分が確認 |
| テストを書かない | 追加開発で既存機能が壊れる | 機能ごとにテスト |

---

## 🤖 「AIを使ったこと」は隠さなくていい

> 💬 「AIで作ったって、面接で不利にならない？」

なりません。むしろ逆です。実務ではAI活用が当たり前になりつつあります。
評価されるのは「AIを使ったかどうか」ではなく、**「AIをどう使いこなしたか」**です。

面接でこう語れれば、強い：

> 「基本機能はAIにたたき台を出させ、私はこの教材で作ったチェックリストで
> mass assignment・認可・N+1をレビューしました。特に購入処理の二重販売は、
> AIの初回コードにロックが無かったので、トランザクションと `lockForUpdate` を
> 自分で追加しました。テストで回帰も担保しています。」

これは「AIに使われる人」ではなく「AIを使う人」の語り口です。この教材が目指した姿です。

## 🔧 やってみよう（演習）

6-4で企画したアプリの**最初の1機能**を、このサイクルで実装します。

1. 1機能を選び、テーブル・ルートを設計する（①）
2. 前提を渡してAIにたたき台を書かせる（②）
3. 全行を読み、分からない行はAIに説明させる（③）
4. 自分の環境で動かす（④）
5. チェックリストでレビューし、問題を見つけて直す（⑤⑥）
6. テストを書いて通す（⑦）
7. commit する（⑧）
8. 「この機能をなぜこう作ったか」を30秒で説明する練習をする
