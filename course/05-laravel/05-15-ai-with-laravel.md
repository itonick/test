# 5-15 🤖 AIにLaravelの設計を相談する

> ◎ **このレッスンのゴール**
> - AIを「コードを書かせる道具」から「設計を一緒に考える相棒」に引き上げる
> - Laravelアプリの設計（テーブル・ルート・責務分担）をAIと詰められる
> - AIの提案を、これまで学んだ観点でレビューして採否を決められる

所要 120分 / 難度 🟡

---

## 📖 いよいよ「AIに設計を相談する」段階へ

第0部では「AIの答えを疑う」、各部では「AIのコードをチェックする」を練習してきました。
ここまで来たあなたは、**AIと設計レベルの対話ができる**土台ができています。

これまで（初級のAIの使い方）：
> 「投稿フォームのコードを書いて」→ 出てきたコードを検証する

これから（中級のAIの使い方）：
> 「フリマアプリを作りたい。テーブル設計とルート設計を一緒に考えて」
> → **提案を評価し、質問し、方針を決める**

コードを書くのはAIでもいい。でも「**どう作るか**」を決めるのはあなたです。
そのためには、AIに良い問いを投げ、返ってきた設計を吟味する力が要ります。

---

## ✍️ 手を動かす① ─ 設計相談の「良いプロンプト」

丸投げ（「フリマアプリ作って」）ではなく、**制約と前提を渡す**のがコツです。

### 悪いプロンプト

```
Laravelでフリマアプリを作って。
```

→ 何でもありの巨大なコードが出てきて、理解も検証もできない。

> 🆘 **ここで詰まったら**（相談したら、いきなり大量のコードが返ってきた）
> - **やること**：プロンプトの冒頭で **「まずコードは書かず、設計だけ相談させてください」** と縛る（下の良いプロンプト参照）。それでもコードを出してきたら「設計の合意ができるまでコードは不要です」と押し戻す
> - **設計が妥当か不安なとき**：この後のチェックリスト（テーブル・リレーション・認可）で採点し、気になる点を**追い質問**する。AIは聞かれないと穴を言いません
> - **最後は自分の言葉でまとめ直す**：AIの回答をコピペした設計書は「理解していない設計書」。自分で書き直せて初めて次に進めます。

```
Laravel 11 でフリマアプリを設計したいです。まずコードは書かず、設計だけ相談させてください。

【作りたい機能】
- ユーザー登録・ログイン（Breeze想定）
- 商品を出品（画像1枚、タイトル、説明、価格）
- 商品一覧・詳細・検索
- 商品を購入する（購入したら他の人は買えない）
- 自分の出品・購入履歴を見る

【前提】
- この教材で PDO/SQL/Eloquent/認可/テストは学習済み
- まずは MVP（最小構成）から

次を提案してください：
1. 必要なテーブルと主なカラム、テーブル間のリレーション
2. 主なルート一覧（メソッド・パス・認証/認可の要否）
3. 「購入済みの商品は買えない」をどう表現するか（状態の持ち方）
4. 最初に作るべき順番（どこから手をつけるか）
```

ポイント：

- **「まずコードは書かず設計だけ」**と縛る → いきなり大量コードを防ぐ
- **機能・前提・欲しいアウトプット**を分けて書く
- **判断が要る所（購入済みの表現）を名指し**で聞く

---

## ✍️ 手を動かす② ─ 返ってきた設計をレビューする

AIが設計を返してきたら、これまでの各部の知識で**採点**します。

### テーブル設計のチェック（第4部の力）

- [ ] 正規化されているか？（同じ情報を複数テーブルに重複して持っていないか）
- [ ] 適切な**外部キー**があるか？（`orders.user_id`, `orders.product_id` など）
- [ ] NULL を許す列は妥当か？（第4部「NULLは慎重に」）
- [ ] 検索する列に**インデックス**の話があるか？

### リレーション設計のチェック（5-8の力）

- [ ] `hasMany` / `belongsTo` / `belongsToMany` の**向き**は正しいか
- [ ] 一覧で **N+1** が起きない設計か（`with()` を使う前提になっているか）

### 認証・認可のチェック（5-10, 5-11の力）

- [ ] 「ログイン必須」の操作に `auth` が想定されているか
- [ ] 「自分のものだけ操作できる」に**ポリシー**が想定されているか
- [ ] `user_id` をフォーム入力から受け取る危険な設計になっていないか

### 「購入済みは買えない」のチェック（状態設計）

- [ ] 状態をどこに持つ？（`products.status` か、`orders` の有無か）
- [ ] **同時に2人が買う**競合をどう防ぐ？（トランザクション／在庫の考え方＝第4部）

> 🧠 **AIの設計は「たたき台」として超優秀**。でも上のチェックを通すと、
> だいたい1〜2個は「あれ、ここ甘くない？」が見つかります。それを指摘して直させるのが、
> あなたの本当の仕事です。

---

## ✍️ 手を動かす③ ─ 深掘りの「追い質問」

一度の回答で終わらせず、**弱い所を突く**質問を返します。

```
「購入済みの商品は買えない」について、products.status を 'on_sale'/'sold' で
持つ案を提案してくれましたが、2人が同時に購入ボタンを押したらどうなりますか？
両方 'sold' になって二重販売にならないか、トランザクションでどう防ぐか、
第4部で学んだロックの考え方も含めて説明してください。
```

こう聞くと、AIは「排他制御・トランザクション・`lockForUpdate()`」といった、
**設計の穴**に踏み込んだ答えを返します。**あなたが穴を知っているから、聞ける**のです。

> ⚠️ **AIは聞かれないと言わない**ことが多い。
> 「同時購入」「巨大データ」「不正入力」など、**起きにくいが起きたら痛い**ケースは、
> あなたから水を向けないと出てこないことがあります。これは第0部から一貫したテーマです。

---

## ✍️ 手を動かす④ ─ 設計を「自分の言葉」で確定させる

AIとの対話が終わったら、**自分でまとめ直す**。ここが一番大事。

- AIの回答をコピペした設計書 → 理解していない設計書（危険）
- 自分の言葉で書き直した設計書 → 理解した設計書（次に進める）

まとめの例（フリマアプリMVP）：

```
テーブル：
  users（Breeze標準）
  products（id, user_id出品者, title, description, price, image_path, status, timestamps）
  orders（id, user_id購入者, product_id, timestamps）

状態：
  products.status = 'on_sale' | 'sold'
  購入時：トランザクション内で status を確認→'sold'に更新→orders作成
         （同時購入は lockForUpdate で防ぐ）

ルート（抜粋）：
  GET  /products            一覧（誰でも）
  GET  /products/{product}  詳細（誰でも）
  GET  /products/create     出品フォーム（auth）
  POST /products            出品（auth）
  POST /products/{product}/purchase  購入（auth, 自分の商品は買えない=policy）

認可：
  出品の編集/削除：出品者本人のみ（ProductPolicy）
  購入：ログイン必須／自分の出品は購入不可
```

> 🧠 **この設計書が、次の総合演習（5-16）の設計図**になります。
> AIと作り、自分の言葉で確定させたこの図を持って、実装に入りましょう。

---

## ⚠️ AIに設計を相談するときの注意

| 落とし穴 | どうする |
| --- | --- |
| いきなり大量のコードが出る | 「まず設計だけ」と縛る |
| もっともらしいが穴がある | 各部のチェックリストで採点する |
| 起きにくい事故に触れない | 「同時に」「大量に」「不正な」で追い質問 |
| 理解しないままコピペ | 自分の言葉で設計書を書き直す |
| 最新でない書き方 | バージョン（Laravel 11）を明示、公式ドキュメントで裏取り |

---

## 🤖 まとめ：AIとの付き合い方（第5部版）

第0部からの学びを、設計レベルに引き上げると：

1. **前提と制約を渡す** … 良い問いが良い設計を引き出す
2. **提案は採点する** … これまでの全知識がレビュー基準になる
3. **穴を突く追い質問** … 知っている人だけが聞ける
4. **自分の言葉で確定** … 理解していない設計は使わない
5. **裏取りする** … バージョン・公式ドキュメント

> AIは「知識のある人」を最強に加速し、「知識のない人」を静かに事故に導きます。
> ここまで手を動かしてきたあなたは、前者になる準備ができています。
