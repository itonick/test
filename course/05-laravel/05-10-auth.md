# 5-10 認証機能（Breeze）

> ◎ **このレッスンのゴール**
> - Laravel Breeze で、ログイン・新規登録・ログアウトを一気に導入できる
> - 「ログインしている人だけ」ページを制限できる（`auth` ミドルウェア）
> - 第3部で自作したセッション・`password_hash` が、どう置き換わるか理解する

所要 180分 / 難度 🟡 ／ 🏁 成果物：ログイン付きアプリ

---

## 📖 認証（Authentication）＝「あなたは誰か」を確かめる

第3部で、あなたはログイン機能を自分で作りました。

- 登録時：`password_hash()` でパスワードをハッシュ化して保存
- ログイン時：`password_verify()` で照合し、`$_SESSION['user_id']` に記録
- 保護ページ：`if (!isset($_SESSION['user_id'])) { リダイレクト }`

**この一連の仕組みは、実は毎回ほぼ同じ**です。だから Laravel には
「認証まわりを丸ごと生成してくれる」公式スターター **Breeze** があります。

> ⚠️ **「自作したのは無駄だった」ではない**
> 逆です。第3部で**中身を自分で作った**からこそ、Breeze が裏で何をしているかが分かる。
> 仕組みを知らずに `install` する人と、知って使うあなたとでは、トラブル時の強さが段違いです。

---

## ✍️ 手を動かす① ─ Breeze を入れる

```bash
composer require laravel/breeze --dev

php artisan breeze:install

# インストール時に「Blade」を選ぶ（この教材ではBladeで進めます）

npm install
npm run build            # 画面のCSS/JSをビルド

php artisan migrate      # users テーブルなどが作られる
```

これだけで、次の画面と機能が**すべて生成**されます。

- `/register` … 新規登録
- `/login` … ログイン
- `/logout` … ログアウト
- `/dashboard` … ログイン後のページ（`auth` で保護済み）
- パスワード再設定、メール確認などの土台

第3部で1つずつ手書きした画面が、コマンド一発で出てきました。

> 🆘 **ここで詰まったら**（Breeze導入後、画面が崩れる／CSSが効かない）
> - **まず確認**：① `npm install` と `npm run build` を実行したか（ビルドしないとCSS/JSが生成されません ─ ここが最頻出）② `php artisan migrate` を実行したか（未実行だと `users` テーブルが無く、登録・ログインで落ちる）③ `.env` のDB設定は合っているか
> - **`npm: command not found`**：Node.js が未インストール。Node を入れてから `npm install`
> - **直らなければ、AIにこう聞く**（実行したコマンドの順番とエラーを貼る）：
>   「Laravel Breeze を入れましたが画面のスタイルが当たりません。実行したコマンドはこれです。原因と確認手順を教えてください」

## ✍️ 手を動かす② ─ 何が置き換わったのかを確認する

Breeze が生成したコードを、第3部の自作コードと並べて見てみましょう。

| 第3部（自作） | Laravel / Breeze |
| --- | --- |
| `password_hash($pw, PASSWORD_DEFAULT)` | 登録時に自動でハッシュ化（`Hash::make` 相当） |
| `password_verify($pw, $hash)` | ログイン時に `Auth::attempt()` が照合 |
| `$_SESSION['user_id'] = $id;` | `Auth::login($user)`（セッション管理はLaravelが担当） |
| `$_SESSION['user_id'] ?? null` | `auth()->user()` / `Auth::user()` |
| `if (!isset($_SESSION['user_id']))` | `auth` ミドルウェア |
| セッション固定化対策を手書き | Breezeが自動で `session()->regenerate()` |

**発想は第3部とまったく同じ**。書く量が激減しただけ、と分かればOKです。

> 🔒 パスワードは Breeze でも**平文では保存されません**。DBの `users.password` を
> 覗くと、第3部で見たのと同じ**ハッシュ文字列**が入っています（自分で確認してみましょう）。

## ✍️ 手を動かす③ ─ ログイン必須ページを作る（`auth` ミドルウェア）

「ログインした人だけ投稿できる」を実現します。第3部の `if (!isset(...))` に相当します。

### ルートで守る

```php
// routes/web.php
use App\Http\Controllers\PostController;

// 誰でも見れる：一覧・詳細
Route::get('/posts', [PostController::class, 'index'])->name('posts.index');
Route::get('/posts/{post}', [PostController::class, 'show'])->name('posts.show');

// ログイン必須：作成・保存・削除
Route::middleware('auth')->group(function () {
    Route::get('/posts/create', [PostController::class, 'create'])->name('posts.create');
    Route::post('/posts', [PostController::class, 'store'])->name('posts.store');
    Route::delete('/posts/{post}', [PostController::class, 'destroy'])->name('posts.destroy');
});
```

`middleware('auth')` の中に入れたルートは、**未ログインだと自動で `/login` に飛ばされます**。
第3部の「未ログインならリダイレクト」を、1行の宣言で実現できました。

---

## ✍️ 手を動かす④ ─ ログインユーザーを使う

### コントローラで「今の人」を取る

```php
public function store(StorePostRequest $request)
{
    $post = $request->user()->posts()->create($request->validated());
    // ↑ ログイン中のユーザーに、投稿をひも付けて作成（user_id が自動で入る）

    return redirect()->route('posts.index')->with('status', '投稿しました');
}
```

`$request->user()`（または `auth()->user()`）で、ログイン中のユーザーモデルが取れます。
5-8 の `hasMany` リレーションと組み合わせると、`->posts()->create()` で
**user_id を自分でセットせずに**投稿を作れます（付け忘れ・なりすまし防止にもなる）。

### Blade で出し分ける

```blade
@auth
    <p>こんにちは、{{ auth()->user()->name }} さん</p>
    <form method="POST" action="{{ route('logout') }}">
        @csrf
        <button>ログアウト</button>
    </form>
@else
    <a href="{{ route('login') }}">ログイン</a>
    <a href="{{ route('register') }}">新規登録</a>
@endauth
```

- `@auth ... @endauth` … ログインしている人にだけ表示
- `@guest ... @endguest` … ログインしていない人にだけ表示

## ✍️ 手を動かす⑤ ─ 動作を確かめる

1. `/register` で新規登録 → 自動でログイン状態になり `/dashboard` へ
2. `/logout`（ボタン）でログアウト
3. ログアウトした状態で `/posts/create` を開く → **`/login` に飛ばされる**（＝保護できている）
4. ログインし直して `/posts/create` → 今度は開ける
5. 投稿してみて、`posts.user_id` に自分のIDが入っていることをDBで確認

> 💡 手順3が確認できたら、認証の一番大事な部分「守れている」が動いた証拠です。

## ⚠️ つまずきポイントまとめ

| 症状 | 原因 | 対処 |
| --- | --- | --- |
| 画面が真っ白／CSSが効かない | `npm run build` していない | `npm install && npm run build` |
| `/login` に何度も飛ばされる | 保護ページにミドルウェアの掛け方ミス | `auth` を掛ける範囲を見直す |
| `auth()->user()` が null | 未ログイン、またはミドルウェア外 | `@auth` で分岐、または `auth` ミドルウェア内で使う |
| 登録できるがログインできない | メール/パスワードの検証やカラム不一致 | Breeze標準の `users` を勝手に壊していないか確認 |
| 419 | `@csrf` 忘れ（ログアウトフォームにも必要） | フォームに `@csrf` |

## 🤖 AIに聞いてみよう

認証は**セキュリティ直結**。AIの答えを一番慎重に扱うべき領域です。

### 使えるプロンプト例

```
Laravel Breeze を入れた前提で、次を実装したいです。
- 投稿の一覧・詳細は誰でも閲覧可
- 作成・削除はログインユーザーのみ
- 投稿は必ずログインユーザーに紐づく
ルート定義とコントローラの該当部分を示してください。
```

### 🔍 AIの答えを疑うチェックリスト

- [ ] パスワードを**平文で保存・比較**していないか（絶対NG。ハッシュ必須）
- [ ] 保護すべきルートに `auth` ミドルウェアが掛かっているか
- [ ] `user_id` をフォーム入力から受け取っていないか（**なりすまし**の穴。`auth()->user()->posts()->create()` を使う）
- [ ] ログイン後に `session()->regenerate()` 相当（セッション固定化対策）がされているか（Breezeは標準で実施）
- [ ] 「認証（誰か）」と「認可（何をしてよいか）」を混同していないか（認可は次回5-11）

> 🧠 **認証のコードは、動いても“安全とは限らない”**
> 第3部で学んだ脅威（平文保存・なりすまし・セッション固定化）を思い出しながら、
> AIのコードを**セキュリティ観点で**レビューしてください。ここが一番差が出ます。

## ✅ 章末チェック

1. Breeze が肩代わりしてくれる処理を、第3部で自作した機能に対応づけて3つ挙げよ。
2. `auth` ミドルウェアは何をするか。第3部の何に相当するか。
3. 投稿を `auth()->user()->posts()->create()` で作ると、なぜ「なりすまし」に強いのか。
4. 「認証（authentication）」と「認可（authorization）」の違いを一言で。

> 認証で「あなたが誰か」は分かりました。次回は「**あなたはこの操作をしてよいか**」＝
> 認可（ポリシー）です。第3部で作った「自分の投稿だけ削除できる」制御を、Laravel流に作り直します。
