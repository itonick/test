# 3-11 AIにコードレビューさせる

> ◎ **このレッスンのゴール**
> - PHPコードのセキュリティレビューを、AIに正しくやらせる
> - AIが見落とす領域を知り、自分で補える
> - レビュー結果を「直す」のではなく「学ぶ」に変える

所要 120分 / 難度 🟡

---

## 📖 PHPは「セキュリティレビューが最も効く」言語

第1部（CSS）ではデザイン、第2部（JS）では設計が主なレビュー対象でした。
**PHPでは、セキュリティが最大の論点になります。**

理由は単純で、**サーバー側のコードだから**です。

| 層 | ミスの影響 |
| --- | --- |
| CSS | 見た目が崩れる |
| JavaScript | その人の画面だけおかしくなる |
| **PHP** | **全ユーザーのデータが漏洩する / サーバーが乗っ取られる** |

---

## 📖 AIがPHPで指摘できること / できないこと

### ✅ AIが得意な領域

| 領域 | 例 |
| --- | --- |
| **エスケープ漏れ** | `<?= $x ?>` を `<?= e($x) ?>` にすべき |
| SQLインジェクション | 文字列連結でSQLを組んでいる（第4部） |
| CSRF対策の欠落 | トークン検証がない |
| 型の問題 | `strict_types` がない、型宣言が甘い |
| 非推奨関数 | `mysql_*`、`ereg`、`create_function` |
| PSR規約 | 命名、インデント、ファイル構成 |
| 例外処理の不足 | ファイル操作の失敗を想定していない |

### ❌ AIが苦手・見落とす領域

| 領域 | なぜ見落とすか |
| --- | --- |
| **認可の抜け** | 「このユーザーがこの投稿を消してよいか」は業務ルール。コードだけでは判断できない |
| **業務ロジックの誤り** | 「税率が10%でよいのか」は仕様の問題 |
| **競合状態** | 「同時アクセス時に二重登録される」は実行順序の問題 |
| **設定ファイル** | `.htaccess`、`php.ini`、ファイル権限は、貼らないと見えない |
| **全体の整合性** | 1ファイルだけ貼ると、他のファイルとの矛盾は見えない |

> ⚠️ **「AIがOKと言ったから安全」ではありません。**
> AIは**貼られたコードの範囲でしか**判断できません。
> **認可の抜けは、自分でチェックリストを作って確認してください。**

## ✍️ 手を動かす① ─ レビュー用プロンプト（PHP版）

**必ず新しい会話で投げてください。**（同じ会話だと、自分の出力を庇う傾向があります）

```text
以下は、PHP で書かれた Web アプリケーションのコードです。
一般ユーザーからの入力を扱います。

【実行環境】
PHP 8.2 / Apache / フレームワークなし

【このコードの役割】
（1〜2文で説明）

【コード】
（ファイル全体を貼る。複数ファイルなら、ファイル名を明記して並べる）

---

以下の観点で、厳しくレビューしてください。

## セキュリティ（最優先）
1. XSS — 出力エスケープの漏れ、文脈に合わないエスケープ
2. CSRF — トークンの生成・検証、GET で状態を変えていないか
3. SQLインジェクション — プレースホルダを使っているか
4. ファイルアップロード — 拡張子偽装、ディレクトリトラバーサル
5. ヘッダーインジェクション — header() に外部入力を渡していないか
6. オープンリダイレクト — Location に外部入力を渡していないか
7. 認証・セッション — session_regenerate_id、Cookie属性、パスワードの扱い
8. 情報漏洩 — エラーメッセージ、デバッグ出力、公開ディレクトリの構成

## 正しさ
9. 入力検証の不足（型・範囲・ホワイトリスト）
10. 日本語（マルチバイト）の扱い
11. 例外・エラー処理の不足
12. 境界値・異常系で壊れる箇所

## 設計
13. 責務の分離（ロジックと表示、データアクセス）
14. 重複コード
15. 命名

---

【出力の形式】
- 各指摘に優先度（🔴致命的 / 🟡要修正 / 🟢改善提案）を付ける
- 「なぜ危険か」「攻撃されると何が起きるか」を必ず書く
- **修正後のコードは書かないでください。** 私が自分で直します
- 問題がない項目は「問題なし」と明記してください

【最後に】
このコードで、あなたが判断できなかった項目
（設定ファイル、他のファイルとの関係、業務ルールなど）を列挙してください。
```

> 💡 **最後の「判断できなかった項目」を聞くのが重要です。**
> AIの守備範囲外を明示させることで、**自分でチェックすべき箇所がわかります。**

## ✍️ 手を動かす② ─ 認可のチェックは自分でやる

**AIが最も見落とすのが、認可（Authorization）です。**

```php
<?php
// AIは「XSSなし、CSRFあり、型OK」と評価するかもしれない
if ($_SERVER["REQUEST_METHOD"] === "POST") {
    if (!csrf_verify($_POST["_csrf_token"] ?? null)) { exit; }

    $post_id = $_POST["post_id"] ?? "";
    $repository->delete($post_id);      // ← ★ 誰でも、誰の投稿でも消せる

    header("Location: index.php", true, 303);
    exit;
}
```

**このコードには致命的な欠陥があります。** ログイン中のユーザーが、
**他人の投稿IDを指定するだけで削除できます。**

### 認可のチェックリスト（自作してください）

**状態を変える処理すべてに対して、以下を確認します。**

```
□ ログインが必要な処理か？ → require_login() があるか
□ 「自分のデータ」だけを操作できるようになっているか？
□ IDを書き換えて、他人のデータを操作できないか？
□ 管理者だけの機能に、一般ユーザーがアクセスできないか？
□ 一覧に表示されないデータでも、IDを直接指定すれば見られないか？
```

### 正しい実装

```php
<?php
$post_id = $_POST["post_id"] ?? "";
$post = $repository->find($post_id);

// ① 存在確認
if ($post === null) {
    http_response_code(404);
    exit("投稿が見つかりません");
}

// ② ★ 所有者確認（これがAIに見落とされる）
if ($post->userId !== current_user()["id"]) {
    http_response_code(403);
    exit("この操作を行う権限がありません");
}

$repository->delete($post_id);
```

> ⚠️ **これは IDOR（Insecure Direct Object Reference）と呼ばれる、
> 実際の Web サービスで最も多い脆弱性の1つ**です。
>
> **URLやフォームのIDを書き換えて試す**という手動テストを、必ず自分でやってください。

## ✍️ 手を動かす③ ─ AIの出力を検証する

### AIが「安全です」と言ったコードを疑う

```text
先ほど「問題なし」と判断されたコードについて、追加で確認させてください。

1. このコードで、ログイン中のユーザーAが、ユーザーBのデータを
   操作できてしまう可能性はありますか？
2. リクエストのパラメータ（ID など）を書き換えた場合、
   どんな問題が起きえますか？
3. 同時に2つのリクエストが来た場合に、問題は起きますか？
4. このコードが依存している「前提」を列挙してください
   （呼び出し元が検証済みである、設定ファイルが正しい、など）

その前提が崩れた場合に何が起きるかも教えてください。
```

> 💡 **「前提を列挙させる」のが強力です。**
> AIは暗黙のうちに「呼び出し元で検証済みだろう」と仮定していることがあります。
> **その仮定が明示されると、自分で確認できます。**

> 🆘 **ここで詰まったら**（AIが「問題なし」と言うが、本当に信じていいか不安）
> - **やること**：**新しい会話**を開いて、同じコードをもう一度レビューさせる。同じ会話だとAIは自分の前の判断を庇いがちなので、別会話のほうが厳しく見ます
> - **こう聞く**：
>   「これはセキュリティ監査です。次のコードを、SQLインジェクション・XSS・CSRF・認可漏れ・機密のハードコーディングの観点で厳しくレビューしてください。問題がなければ『問題なし』と明言してください。（コードを貼る）」
> - それでも不安が残るセキュリティの最終判断は、**人間（あなた）が負う**もの。これは 0-7・6-7 で繰り返し出てくる原則です。

### 指摘が正しいか検証する

**AIの指摘も、鵜呑みにしてはいけません。**

```text
以下の指摘をいただきました。

（AIの指摘を貼る）

この指摘について確認させてください。

1. この指摘は、私のコードの文脈で本当に問題になりますか？
2. 具体的にどんな入力・操作をすると、問題が顕在化しますか？
3. 私が自分で再現・確認する手順を教えてください
4. この指摘が「過剰」である可能性はありますか？
```

**「再現手順」を聞くのがポイントです。** 再現できない指摘は、
このコードには当てはまらない可能性があります。

## ✍️ 手を動かす④ ─ レビューを「学び」に変える

**指摘を直して終わりにすると、次も同じミスをします。**

### 学習ログの型

```markdown
## 2026-04-20 セキュリティレビュー（contact.php）

### 🔴 指摘1: nl2br の順序が逆
- **何が問題か**: `e(nl2br($x))` だと `<br>` までエスケープされ、
  改行が `&lt;br&gt;` として表示される。逆に `nl2br($x)` を先にすると
  XSS が通る
- **なぜやってしまったか**: 「改行を変換してからエスケープ」と
  順番を逆に覚えていた
- **今後の防ぎ方**: `white-space: pre-wrap` を使う。
  そもそも HTML を生成しない設計にする
- **同じミスが他にないか**: `board.php` の本文表示も確認 → 同じ問題あり。修正済み

### 🟡 指摘2: ...
```

**「なぜやってしまったか」と「同じミスが他にないか」が重要です。**

- 前者は、**思い込みの修正**になる
- 後者は、**横展開**になる（1か所直しても、他に残っていたら意味がない）

### 自分専用チェックリストを育てる

`appendix/my-checklist.md` を作り、指摘されるたびに追加してください。

```markdown
# 自分専用 PHP チェックリスト

## 出力
- [ ] すべての `<?=` に `e()` を通したか
- [ ] `href` / `src` は `safe_url()` を通したか
- [ ] JavaScript に埋めるときは `json_encode()` か
- [ ] `nl2br(e($x))` の順序になっているか

## 入力
- [ ] すべての受け取りに `?? ""` を付けたか
- [ ] 数値は `(int)` で変換したか
- [ ] select / radio の値をホワイトリスト検証したか

## 認可（★AIが見落とす）
- [ ] 状態を変える処理に `require_login()` があるか
- [ ] IDを書き換えて他人のデータを操作できないか
- [ ] 管理者専用機能を一般ユーザーが叩けないか

## セッション
- [ ] ログイン時に `session_regenerate_id(true)` を呼んだか
- [ ] Cookie に `httponly` と `samesite` を設定したか

## 保存
- [ ] `file_put_contents` に `LOCK_EX` を付けたか
- [ ] データファイルは公開ディレクトリの外にあるか
```

> 💡 **このチェックリストが、あなたの資産です。**
> 数ヶ月続けると、市販の書籍より自分に合ったものになります。

## ✍️ 手を動かす⑤ ─ 実践：欠陥のあるコードをレビューする

以下は、**掲示板の投稿処理**です。**8つの問題**があります。

**まず自分で全部見つけてから**、AIにレビューさせて比較してください。

```php
<?php
session_start();
$posts_file = "posts.json";

if ($_POST) {
    $name = $_POST["name"];
    $body = $_POST["body"];

    if ($name && $body) {
        $posts = json_decode(file_get_contents($posts_file), true);
        $posts[] = [
            "id" => count($posts) + 1,
            "name" => $name,
            "body" => $body,
            "ip" => $_SERVER["REMOTE_ADDR"],
            "time" => date("Y-m-d H:i:s"),
        ];
        file_put_contents($posts_file, json_encode($posts));
        echo "投稿しました";
    } else {
        echo "入力してください";
    }
}

$posts = json_decode(file_get_contents($posts_file), true);
?>
<form method="post">
  名前: <input type="text" name="name"><br>
  本文: <textarea name="body"></textarea><br>
  <input type="submit" value="投稿">
</form>

<?php foreach ($posts as $post) { ?>
  <div>
    <b><?= $post["name"] ?></b>
    <span><?= $post["time"] ?></span>
    <p><?= nl2br($post["body"]) ?></p>
    <a href="delete.php?id=<?= $post["id"] ?>">削除</a>
  </div>
<?php } ?>
```

<details>
<summary>答えを見る（自分で8つ探してから開いてください）</summary>

### 🔴 致命的

**1. XSS（複数箇所）**
`<?= $post["name"] ?>` と `<?= nl2br($post["body"]) ?>` がエスケープされていない。
投稿本文に `<script>` を入れると、**全閲覧者のブラウザで実行**される。

**2. GET で削除している**
`<a href="delete.php?id=...">削除` は、`<img src="delete.php?id=1">` を
どこかに貼られるだけで実行される。**POST + CSRFトークン**にする。

**3. CSRFトークンがない**
投稿処理自体も、外部サイトから勝手に実行できる。

**4. 認可がない**
誰でも、誰の投稿でも削除できる（IDOR）。

**5. データファイルが公開ディレクトリにある**
`posts.json` に直接アクセスすると、**IPアドレスを含む全データがダウンロードできる**。
公開ディレクトリの外に置くか、`.htaccess` で拒否する。

### 🟡 要修正

**6. IDの採番が壊れる**
`count($posts) + 1` は、削除があると重複する。
3件（1,2,3）→ 2番を削除 → 2件 → 次の投稿が `id: 3` で重複。
`bin2hex(random_bytes(8))` などを使う。

**7. 排他制御がない**
`file_put_contents` に `LOCK_EX` がなく、`load` と `store` の間にも隙がある。
同時投稿でデータが消える（競合状態）。

**8. 入力検証が不十分**
- `?? ""` がない → Warning
- `if ($name && $body)` は `"0"` を弾いてしまう
- 文字数の上限がない → 1MBの本文を投稿できる
- 制御文字を除去していない

### 🟢 その他

- `$_POST` を条件に使っている
- PRG パターンでない（リロードで二重投稿）
- `json_decode` の結果が `null` の可能性を考慮していない（初回アクセスでエラー）
- IPアドレスを保存しているが、個人情報の扱いとして告知が必要
- `<label>` がない
- 0件のときの表示がない

</details>

### AIと比較する

自分で見つけた数と、AIが指摘した数を比べてください。

| | 自分 | AI |
| --- | --- | --- |
| 見つけた問題の数 | | |
| 🔴致命的を見つけられたか | | |
| **認可の抜け（4番）を指摘できたか** | | |
| データファイルの公開（5番）を指摘できたか | | |

> 💡 **AIは 4番（認可）と 5番（ファイル配置）を見落とすことがあります。**
> 見落としたら、それが「AIの守備範囲外」の実例です。

## 🤖 追加のプロンプト

### ① 攻撃者視点でのチェックリストを作らせる

```text
以下のWebアプリについて、「攻撃者ならどこを試すか」の
チェックリストを作ってください。

（機能一覧とコードを貼る）

条件:
- 実際に動く攻撃コードは書かないでください
- 「試す操作」と「それで何がわかるか」の形式で
- 私が自分の環境で安全に確認できる手順にしてください
- URLパラメータやフォーム値の改ざんを含めてください

```

### ② コードの前提を明示させる

```text
以下の関数について、暗黙の前提を列挙してください。

（関数を貼る）

- 呼び出し元に期待していること
- 引数に期待していること（検証済みか、型、範囲）
- 環境に期待していること（設定、ディレクトリの存在、権限）
- 同時実行されないことを前提にしていないか

それぞれの前提が崩れた場合、何が起きるかも教えてください。
```
