## 📖 第3部の掲示板は、何件で壊れるのか

第3部で作った掲示板は、JSONファイルにデータを保存していました。

```php
// 1件取得するためだけに、全件を読み込んでいる
public function find(string $id): ?Post
{
    foreach ($this->all() as $post) {   // ← all() は JSON 全体を読んでパースする
        if ($post->id === $id) return $post;
    }
    return null;
}
```

**投稿が増えたときに何が起きるか、実際に測ってみましょう。**

### 実験：件数を増やして測る

`php-lesson/benchmark.php`（📋 コピペ可）

```php
<?php
declare(strict_types=1);

/**
 * 指定件数のダミーデータを作り、「1件検索」にかかる時間を測る
 */
function benchmark(int $count): array
{
    $path = __DIR__ . "/bench.json";

    // ---------- データを作る ----------
    $rows = [];
    for ($i = 0; $i < $count; $i++) {
        $rows[] = [
            "id"         => bin2hex(random_bytes(8)),
            "name"       => "ユーザー{$i}",
            "body"       => str_repeat("これはテスト投稿です。", 5),
            "created_at" => time() - $i,
        ];
    }
    file_put_contents($path, json_encode($rows));
    $file_size = filesize($path);

    // 最後の1件のIDを検索対象にする（最悪ケース）
    $target = $rows[$count - 1]["id"];

    // ---------- 1件検索を10回行う ----------
    $start = hrtime(true);

    for ($n = 0; $n < 10; $n++) {
        $loaded = json_decode(file_get_contents($path), true);
        foreach ($loaded as $row) {
            if ($row["id"] === $target) break;
        }
    }

    $elapsed_ms = (hrtime(true) - $start) / 1_000_000 / 10;

    unlink($path);

    return [
        "件数"       => number_format($count),
        "ファイルsize" => number_format((int) round($file_size / 1024)) . " KB",
        "1件検索"    => number_format($elapsed_ms, 2) . " ms",
        "メモリ"      => number_format((int) round(memory_get_peak_usage() / 1024 / 1024)) . " MB",
    ];
}

foreach ([100, 1000, 10000, 50000] as $count) {
    print_r(benchmark($count));
}
```

> 💡 桁を揃えて表示する完成版は [`code/04-01/benchmark.php`](../code/04-01/benchmark.php) にあります（📋 コピペ可）。
> `printf("%-10s")` は**バイト数で数えるため、日本語を含むと桁が揃いません**。
> 第3部（3-2）で学んだ「マルチバイト」の話が、ここでも出てきます。

### 実行結果

**実際に測った結果です**（PHP 8.4 / Linux）。環境によって数値は変わりますが、**傾向は必ず同じ**です。

```
件数        ファイルsize    1件検索     メモリ
------------------------------------------------
100         42 KB           0.15 ms     2 MB
1,000       417 KB          1.49 ms     4 MB
10,000      4,179 KB        16.07 ms    16 MB
50,000      20,936 KB       94.26 ms    72 MB
```

**件数が10倍になると、時間も約10倍になります。** これを **O(n)**（線形時間）と呼びます。

### 何が問題なのか

| 件数 | 1件検索 | 同時に10人がアクセスすると |
| --- | --- | --- |
| 100 | 0.15ms | 問題なし |
| 1,000 | 1.5ms | 問題なし |
| 10,000 | 16ms | **サーバーが160ms分の仕事を抱える** |
| 50,000 | 94ms | **約1秒。ユーザーが「重い」と感じ始める** |
| 200,000 | 約380ms | **4秒。離脱される** |

メモリも比例して増えます。50,000件で 72MB、**200,000件なら約290MB**。
PHP のデフォルト上限（`memory_limit = 128M`）を超え、**Fatal error で停止します**。

> 💡 **「1件だけ欲しいのに、20MBのファイルを読んでいる」**——これが問題の本質です。
> データベースなら、**必要な1行だけ**を返します。

> ⚠️ **これは「いつか起きる問題」ではありません。**
> 1日30件の投稿があるサイトなら、**1年で1万件**を超えます。

## 📖 ファイル保存の5つの限界

| # | 限界 | 具体的に |
| --- | --- | --- |
| 1 | **検索が遅い** | 全件を読んで順に調べる（O(n)） |
| 2 | **メモリを食う** | 1件だけ欲しくても全件をメモリに載せる |
| 3 | **複雑な条件が書けない** | 「4月の投稿で、返信が3件以上のもの」を効率よく取れない |
| 4 | **同時アクセスに弱い** | ロックで待たせる。書き込みが直列化する |
| 5 | **途中で壊れる** | 書き込み中に停電すると、JSONが不完全になり**全データが読めなくなる** |

### 5番が最も怖い

```json
[
  {"id": "abc", "body": "投稿1"},
  {"id": "def", "bo
```

**`json_decode` が `null` を返し、全投稿が消えたように見えます。**
1万件のデータが、1回の障害で失われます。

## 📖 データベースが解決すること

| 限界 | データベースでの解決 |
| --- | --- |
| 検索が遅い | **インデックス**により、1万件でも0.1ms程度 |
| メモリを食う | 必要な行だけを返す |
| 複雑な条件 | **SQL** で宣言的に書ける |
| 同時アクセス | **行単位のロック**。他の行は待たない |
| 途中で壊れる | **トランザクション**。「全部成功か、全部取り消し」 |

### インデックスのイメージ

```
インデックスなし（ファイル保存と同じ）
  1件目を見る → 違う
  2件目を見る → 違う
  ... 1万回繰り返す

インデックスあり（本の索引と同じ）
  索引で「id = abc」の位置を引く → 14回の比較で到達
```

**1万件でも14回、100万件でも20回程度**で見つかります（二分探索の原理）。
これが **O(log n)** です。

> 💡 **「なぜ速いのか」を理解しておくと、インデックスを張る場所が自分で判断できます。**
> レッスン 4-5 と 4-8 で詳しく扱います。

## ✍️ 手を動かす① ─ 用語を Excel で理解する

RDB の構造は、**Excel のシートとほぼ同じ**です。

```
テーブル: posts
┌──────┬──────────────┬───────────────────┬─────────────────────┐
│ id   │ name         │ body              │ created_at          │  ← カラム（列）
├──────┼──────────────┼───────────────────┼─────────────────────┤
│ 1    │ 山田太郎     │ はじめまして      │ 2026-04-13 10:05:00 │  ← レコード（行）
│ 2    │ 名無しさん   │ テスト投稿です    │ 2026-04-13 11:20:00 │
│ 3    │ 佐藤花子     │ よろしく          │ 2026-04-14 09:00:00 │
└──────┴──────────────┴───────────────────┴─────────────────────┘
```

| 用語 | Excelでいうと | 意味 |
| --- | --- | --- |
| **データベース** | ブック（ファイル全体） | テーブルの集まり |
| **テーブル** | シート | 1つの種類のデータの表 |
| **カラム（列）** | 列 | 項目。名前と**型**を持つ |
| **レコード（行）** | 行 | 1件分のデータ |
| **主キー** | ID列 | **各行を一意に識別する列** |

### Excel との決定的な違い

| | Excel | データベース |
| --- | --- | --- |
| 型 | セルごとに自由 | **カラム単位で固定**（数値列に文字は入れられない） |
| 制約 | ほぼなし | **NOT NULL、UNIQUE、外部キー**などで守れる |
| 同時編集 | 実質1人 | **何百人でも同時に** |
| 件数 | 100万行で限界 | **数億行でも動く** |
| 検索 | 全体を走査 | **インデックス** |

> 🆘 **ここで詰まったら**（用語が抽象的でイメージできない）
> - **考え方**：この段階は**Excelの例えで十分**です。「テーブル＝シート」「カラム＝列」「レコード＝行」「主キー＝ID列」。手を動かす4-2以降で実物に触れると腹落ちします
> - **理解でつまずいたら、AIに例え話で説明させる**：
>   「『データベース／テーブル／カラム／レコード／主キー』の関係を、プログラミング未経験者に、Excelや図書館など身近な例えで説明してください。専門用語は最後にまとめてください」
| 関係 | VLOOKUP で頑張る | **JOIN** で自然に扱える |

> 💡 **「型と制約でデータを守る」**のが、データベースの重要な役割です。
> 第3部では PHP のコードで検証していましたが、**コードにバグがあれば不正なデータが入ります**。
> データベースの制約は、**最後の砦**として機能します。

## ✍️ 手を動かす② ─ SQL を眺めてみる

SQL（エス・キュー・エル）は、データベースを操作する言語です。

```sql
-- 全件取得
SELECT * FROM posts;

-- 条件をつけて取得
SELECT name, body FROM posts WHERE created_at >= '2026-04-14';

-- 並び替えて上位10件
SELECT * FROM posts ORDER BY created_at DESC LIMIT 10;

-- 件数を数える
SELECT COUNT(*) FROM posts;

-- 追加
INSERT INTO posts (name, body) VALUES ('山田太郎', 'はじめまして');

-- 更新
UPDATE posts SET body = '修正しました' WHERE id = 1;

-- 削除
DELETE FROM posts WHERE id = 1;
```

**注目してほしいのは、「どうやるか」を書いていない**ことです。

```php
// PHP：手順を書く（手続き的）
foreach ($all as $post) {
    if ($post->createdAt >= $threshold) {
        $result[] = $post;
    }
}
usort($result, fn($a, $b) => $b->createdAt <=> $a->createdAt);
$result = array_slice($result, 0, 10);
```

```sql
-- SQL：欲しいものを書く（宣言的）
SELECT * FROM posts WHERE created_at >= '2026-04-14' ORDER BY created_at DESC LIMIT 10;
```

**「どう取ってくるか」はデータベースが最適化して決めます。**
インデックスを使うか、どの順で処理するか——すべて自動です。

> 💡 第2部で `map` / `filter` を学んだときの「宣言的に書く」という考え方の、さらに先にあるものです。

## ✍️ 手を動かす③ ─ データ型を知る

カラムには型を指定します。**よく使うものだけ覚えれば十分です。**

### 数値

| 型 | 範囲 | 使いどころ |
| --- | --- | --- |
| `INT` | 約 ±21億 | **ID、個数、点数**。最もよく使う |
| `BIGINT` | 約 ±922京 | 大規模なID |
| `TINYINT` | -128〜127 | フラグ（0/1）、小さな区分 |
| `DECIMAL(10,2)` | 正確な小数 | **金額**。小数点以下2桁 |
| `FLOAT` / `DOUBLE` | 概数 | 座標、測定値 |

> ⚠️ **金額に `FLOAT` を使わないでください。**
> 第2部（2-9）で見た `0.1 + 0.2 !== 0.3` の問題が起きます。
> **`DECIMAL` を使うか、「円」単位の `INT` で持つ**のが正解です。

### 文字列

| 型 | 最大長 | 使いどころ |
| --- | --- | --- |
| `VARCHAR(n)` | 指定した n 文字 | **名前、メール、タイトル**。最もよく使う |
| `CHAR(n)` | 固定 n 文字 | 郵便番号など、長さが決まっているもの |
| `TEXT` | 約65,000文字 | **本文、説明文** |
| `MEDIUMTEXT` | 約1600万文字 | 非常に長い文書 |

> 💡 **`VARCHAR` と `TEXT` の使い分け**
> - 検索・並び替えの対象になる → `VARCHAR`（インデックスを張れる）
> - 表示するだけの長文 → `TEXT`
>
> **`VARCHAR(255)` は定番の長さ**です。メールアドレスは `VARCHAR(255)`、
> **パスワードハッシュも `VARCHAR(255)`**（3-8 で触れた通り）。

### 日付・時刻

| 型 | 形式 | 使いどころ |
| --- | --- | --- |
| `DATE` | `2026-04-13` | 誕生日、予約日 |
| `DATETIME` | `2026-04-13 10:05:00` | **作成日時**。最もよく使う |
| `TIMESTAMP` | 同上（範囲は1970〜2038） | 自動更新したい場合 |
| `TIME` | `10:05:00` | 営業時間 |

> ⚠️ **`TIMESTAMP` は 2038年で溢れます**（2038年問題）。
> **`DATETIME` を使ってください。**

### その他

| 型 | 使いどころ |
| --- | --- |
| `BOOLEAN` | 真偽値（実体は `TINYINT(1)`。0 か 1） |
| `ENUM('a','b')` | 決まった選択肢（**変更が面倒なので、あまり推奨されない**） |
| `JSON` | 構造化データ（MySQL 5.7以降） |

## ✍️ 手を動かす④ ─ 掲示板のテーブルを設計してみる

第3部の掲示板の JSON を見てください。

```json
{
  "id": "b95ca35d2d7efac1",
  "name": "山田太郎",
  "body": "はじめまして。\nよろしくお願いします。",
  "created_at": 1789282973,
  "edit_token": "696014400190af495f50939ce81623c7"
}
```

これをテーブルにすると、こうなります。

```sql
CREATE TABLE posts (
    id         INT AUTO_INCREMENT PRIMARY KEY,
    name       VARCHAR(30)  NOT NULL,
    body       TEXT         NOT NULL,
    edit_token CHAR(32)     NOT NULL,
    created_at DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

**まだ意味がわからなくて構いません。** 次のレッスンから1つずつ扱います。

ただし、**この時点で気づいてほしい変化**があります。

| JSON | テーブル | 何が良くなったか |
| --- | --- | --- |
| `"id": "b95ca..."` | `INT AUTO_INCREMENT` | **採番をDBに任せられる**（重複しない） |
| `"name"` に何文字でも入る | `VARCHAR(30) NOT NULL` | **30文字を超えるデータが入らない** |
| `"created_at": 1789282973` | `DATETIME` | **日付として比較・絞り込みできる** |
| 型の保証なし | 型が固定 | **数値カラムに文字が入らない** |

> 💡 **`NOT NULL` が重要です。**
> PHPのコードで検証を忘れても、**データベースが空のデータを拒否します**。
> 第3部の `Post::create()` による検証に加えて、**二重の防御**になります。

### `utf8mb4` について

```sql
DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci
```

> ⚠️ **必ず `utf8mb4` を指定してください。`utf8` ではありません。**
>
> MySQL の `utf8` は**1文字3バイトまで**しか扱えず、**絵文字（4バイト）が保存できません**。
> 絵文字を投稿されると、エラーになるか文字化けします。
>
> `utf8mb4` は「UTF-8 の、最大4バイト版」という意味です。**これが本物のUTF-8です。**

## ⚠️ つまずきポイントまとめ

| よくある誤解 | 正しい理解 |
| --- | --- |
| データベースは大規模サイト用 | **1000件を超えたら有効**。小規模でも恩恵がある |
| SQLは難しい | **基本は5つの命令**（SELECT / INSERT / UPDATE / DELETE / CREATE）だけ |
| ファイル保存でも工夫すれば速くできる | **インデックスを自作することになる = DBの再実装** |
| `utf8` を指定すればOK | **`utf8mb4` が必要**（絵文字） |
| 金額は FLOAT | **DECIMAL か INT（円単位）** |
| TIMESTAMP が便利 | **2038年問題。DATETIME を使う** |

| 公開フラグ | `BOOLEAN`（= `TINYINT(1)`） | 0 / 1 |
| 誕生日 | `DATE` | 時刻は不要 |
| 登録日時 | `DATETIME` | **TIMESTAMP は2038年問題** |
| 郵便番号 | `CHAR(8)` | 長さが固定（ハイフン込み8文字） |
| 評価（1〜5） | `TINYINT` | 範囲が小さい。`CHECK` 制約も付けられる |

**価格について**：消費税や割引で小数が出る場合は `DECIMAL(10,2)` を使います。
ただし日本円なら、**「円」単位の `INT` で持ち、計算時に切り捨て/切り上げのルールを明示**するのが確実です。

</details>
