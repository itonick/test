# 4-9 AIにSQLとテーブル設計を相談する

> ◎ **このレッスンのゴール**
> - AIにSQL・テーブル設計を相談し、結果を検証できる
> - AIが生成したSQLの危険な箇所を見抜ける
> - `EXPLAIN` を使って、AIの「速い」という主張を確かめられる

所要 90分 / 難度 🟡

---

## 📖 データベースはAIが得意な領域。だが検証が要る

AIはSQLが得意です。複雑なJOINや集計クエリを、すぐに書いてくれます。
**しかし、データベースのミスは「全ユーザーのデータが漏れる/消える」に直結します。**

第3部（3-11）で、AIが見落とす領域を学びました。データベースでも同じです。

### ✅ AIが得意なこと

| 領域 | 例 |
| --- | --- |
| SQLの構文 | 複雑なJOIN、サブクエリ、ウィンドウ関数 |
| SQL方言の変換 | MySQL → PostgreSQL の書き換え |
| 集計クエリ | GROUP BY、HAVING、CASE の組み合わせ |
| テーブル設計の叩き台 | 正規化された初期案 |
| エラーの解読 | エラーメッセージの意味 |

### ❌ AIが間違える・見落とすこと

| 領域 | 理由 |
| --- | --- |
| **SQLインジェクション対策** | 「動くSQL」を優先し、文字列連結で書くことがある |
| **インデックス設計** | データ量・アクセス頻度を知らないと判断できない |
| **N+1問題** | ループの外の文脈が見えていない |
| **業務ルール** | 「その正規化が妥当か」は仕様次第 |
| **実際の性能** | 「速い」は推測。`EXPLAIN` で確かめるしかない |
| **文字コード** | `utf8` と `utf8mb4` を取り違える |

## ✍️ 手を動かす① ─ テーブル設計を相談する

### 効くプロンプト

```text
【作りたいもの】
（アプリの説明を1〜2文で）

【必要な機能】
-
-

【技術構成】
MySQL 8.0 / InnoDB / 文字コード utf8mb4

【聞きたいこと】
1. 必要なテーブルの一覧と、それぞれの役割
2. 各テーブルのカラム（型・NOT NULL・UNIQUE・デフォルト値つき）
3. テーブル間のリレーション（1対多 / 多対多）と外部キー
4. インデックスを張るべきカラムと、その理由
5. この設計で「同じ情報が2か所にある」箇所と、それが意図的か
6. 将来の拡張で問題になりそうな点

【制約】
- 金額は円単位の整数（INT）で持つこと
- 日時は DATETIME（TIMESTAMP の2038年問題を避ける）
- パスワードは password_hash 用に VARCHAR(255)
- 命名は snake_case、テーブル名は複数形

まず設計方針を説明し、最後に CREATE TABLE を提示してください。
```

> 💡 **「制約」を明示するのが重要です。**
> これを書かないと、AIは金額に `FLOAT`、日時に `TIMESTAMP` を使うことがあります。
> **自分が学んだルールを制約として渡す**——第1部（1-13）から続けている考え方です。

### 受け取ったら検証する

**AIの設計を、4-5のチェックリストで採点してください。**

- [ ] 金額が `INT` または `DECIMAL` になっているか（`FLOAT` はNG）
- [ ] 日時が `DATETIME` になっているか（`TIMESTAMP` に注意）
- [ ] 文字セットが `utf8mb4` か（`utf8` はNG）
- [ ] 多対多に中間テーブルがあるか
- [ ] 外部キーにインデックスが張られているか
- [ ] 「その時点の値」を持つべき箇所（注文時の価格）が考慮されているか
- [ ] `ENGINE=InnoDB` が指定されているか
- [ ] メールアドレスなど、重複を防ぐべきカラムに `UNIQUE` があるか

## ✍️ 手を動かす② ─ 生成されたSQLを検証する

**AIが書いたSQLは、必ず自分の環境で実行してください。**

### 検証の手順

```
① まず SELECT で試す（UPDATE/DELETE をいきなり実行しない）
② 件数を確認する（想定と合うか）
③ EXPLAIN でインデックスが効いているか確認する
④ プレースホルダになっているか確認する（文字列連結は危険）
⑤ エッジケースを試す（0件、NULL、日本語、大量データ）
```

> 🆘 **ここで詰まったら**（AIのSQLをそのまま実行してよいか不安）
> - **鉄則**：AIのSQLは**いきなり `UPDATE`/`DELETE` しない**。まず `SELECT` に置き換えて対象を確認 → 件数を見る → それから変更系を実行。上の手順①〜⑤を必ず通す
> - **「このSQL、速いですよ」が信じられないとき**：`EXPLAIN` を頭に付けて実行し、`type` が `ALL`（全走査）でないか、`key` にインデックスが使われているかを見る（次の③で練習）
> - **AIにこう聞く**（自分の環境で出た `EXPLAIN` の結果を貼る）：
>   「このクエリの EXPLAIN 結果です（貼る）。インデックスは効いていますか？ 遅いなら、どの列にインデックスを張るべきか、理由つきで教えてください」

### ⚠️ AIが文字列連結で書いてきたら

```php
// AIがこう書いてきたら、危険信号
$sql = "SELECT * FROM users WHERE email = '{$email}'";
```

**「動くSQL」を求めると、AIは最短で動くものを出します。**
それがSQLインジェクションの穴を持つことがあります。

**プロンプトに一言加えてください。**

```text
必ずプレースホルダ（プリペアドステートメント）を使ってください。
文字列連結でSQLを組み立てないでください。
ORDER BY やテーブル名など、プレースホルダで扱えない箇所は
ホワイトリスト方式で安全に扱ってください。
```

## ✍️ 手を動かす③ ─ EXPLAIN でAIの「速い」を検証する

**AIは「このクエリは高速です」と言いますが、それは推測です。**

```text
AI:「このクエリはインデックスを使うので高速です」
```

**本当かどうかは、`EXPLAIN` でしか分かりません。**

```sql
EXPLAIN SELECT * FROM posts WHERE user_id = 5 ORDER BY created_at DESC;
```

```
+----+-------+---------------------------+------+------+------------+
| id | table | key                       | rows | type | Extra      |
+----+-------+---------------------------+------+------+------------+
| 1  | posts | idx_posts_user_created    | 3    | ref  |            |
+----+-------+---------------------------+------+------+------------+
```

**確認すること**（4-5で学んだ通り）

| 列 | AIの主張が正しい場合 | 怪しい場合 |
| --- | --- | --- |
| `key` | インデックス名が入っている | **`NULL`（使われていない）** |
| `type` | `ref` / `eq_ref` / `const` | **`ALL`（全件走査）** |
| `Extra` | `Using index` | **`Using filesort` / `Using temporary`** |

### AIに聞き返す

```text
このクエリを EXPLAIN したところ、以下の結果になりました。

（EXPLAIN の結果を貼る）

1. type が ALL になっています。なぜインデックスが使われていないのですか
2. どのインデックスを張れば改善しますか
3. クエリの書き方を変える必要はありますか

「速いはず」ではなく、この EXPLAIN の結果に基づいて説明してください。
```

> 💡 **「速いはず」を「速い（EXPLAINで確認済み）」に変える**のが、
> プロとアマチュアの差です。AIの推測を、事実で裏付けてください。

## ✍️ 手を動かす④ ─ SQLをレビューさせる

**自分が書いたSQLを、AIに厳しくチェックさせます。**

```text
以下は、私が書いた MySQL のクエリです。

【テーブル定義】
（CREATE TABLE を貼る）

【クエリ】
（SQLを貼る）

【このクエリの目的】
（何を取得したいか）

次の観点でレビューしてください。

1. 意図した結果が得られるか（行の重複、0件やNULLの扱い）
2. SQLインジェクションの危険（文字列連結、プレースホルダの漏れ）
3. LEFT JOIN + COUNT(*) の罠、複数の1対多をJOINしたときの掛け算
4. インデックスが効く書き方か（関数で包んでいないか、前方 % の LIKE）
5. N+1問題の可能性
6. より読みやすい・速い書き方

修正後のSQLは書かず、指摘だけをお願いします。
指摘の妥当性を私が EXPLAIN で確認できるよう、
「どう確認すればよいか」も添えてください。
```

## ✍️ 手を動かす⑤ ─ 実践：AIの設計を検証する

**AIに掲示板のテーブル設計をさせ、それを検証してください。**

### ステップ1：設計させる

「手を動かす①」のプロンプトで、以下を設計させます。

```text
【作りたいもの】
会員制の掲示板。会員は投稿・返信・いいねができる。
投稿にはタグを複数つけられる。

【必要な機能】
- 会員登録・ログイン
- 投稿（会員のみ）
- 返信
- いいね（1人1投稿1回）
- タグ（1投稿に複数）
- 投稿の検索・並び替え・ページ送り
```

### ステップ2：チェックリストで採点する

返ってきた設計を、以下で採点してください。

| 項目 | AIの設計 |
| --- | --- |
| `users` に `email` の UNIQUE があるか | |
| パスワードが `VARCHAR(255)` か | |
| `posts.user_id` に外部キーとインデックスがあるか | |
| いいねが「1人1投稿1回」を保証しているか（複合UNIQUE） | |
| タグが中間テーブル（多対多）になっているか | |
| 文字セットが `utf8mb4` か | |
| 日時が `DATETIME` か | |

### ステップ3：「1人1投稿1回」を確認する

**いいねの重複防止は、AIが見落としやすい箇所です。**

```sql
-- ❌ これだと、同じ人が同じ投稿に何回でもいいねできる
CREATE TABLE likes (
    id      INT AUTO_INCREMENT PRIMARY KEY,
    user_id INT NOT NULL,
    post_id INT NOT NULL
);

-- ✅ 複合UNIQUEで防ぐ
CREATE TABLE likes (
    id      INT AUTO_INCREMENT PRIMARY KEY,
    user_id INT NOT NULL,
    post_id INT NOT NULL,
    UNIQUE KEY uk_user_post (user_id, post_id),   -- ★
    ...
);
```

**AIの設計にこれがなければ、指摘して直させてください。**

### ステップ4：主要クエリを書かせて検証する

```text
この設計で、以下のクエリを書いてください。
必ずプレースホルダを使い、EXPLAINで確認できる形にしてください。

1. 投稿一覧（投稿者名・いいね数・返信数・タグを含む、新しい順、10件）
2. ある投稿に、あるユーザーがいいねしているか
3. いいねが多い順の投稿トップ5
4. 特定のタグが付いた投稿の一覧
```

**1番のクエリは、複数の1対多（いいね・返信・タグ）を含みます。**
**JOINの掛け算が起きていないか、必ず確認してください**（4-6で学んだ通り）。

## ⚠️ つまずきポイントまとめ

| AIの落とし穴 | 対策 |
| --- | --- |
| 文字列連結でSQLを書く | プロンプトで「プレースホルダを使う」と指示 |
| `FLOAT` で金額を扱う | 「円単位の INT」と制約を渡す |
| `TIMESTAMP` を使う | 「DATETIME を使う」と指示 |
| `utf8` を指定する | 「utf8mb4」と指示 |
| いいねの重複防止を忘れる | 複合UNIQUEを確認 |
| 「速い」と断言する | `EXPLAIN` で確認 |
| N+1になるPHPコードを出す | ループ内のクエリを確認 |
| JOINの掛け算を見落とす | `DISTINCT` かサブクエリを確認 |

## 🤖 AIに聞いてみよう

### ① SQL方言の違いを確認する

```text
以下は MySQL のクエリです。

（SQLを貼る）

1. このクエリを PostgreSQL で動かす場合、書き換えが必要な箇所はどこですか
2. SQLite の場合はどうですか
3. MySQL 固有の関数（GROUP_CONCAT、DATE_FORMAT など）を使っている箇所と、
   他のDBでの代替を教えてください

将来データベースを移行する可能性を考えて、
「MySQL固有の書き方」と「標準的な書き方」を区別して教えてください。
```

### ② インデックスの判断をさせる（ただし検証必須）

```text
以下のテーブルとクエリについて、インデックスを提案してください。

【テーブル定義】
（CREATE TABLE を貼る）

【よく実行するクエリ】
1.
2.
3.

【データ量の想定】
- posts: 約10万件
- comments: 約50万件
- 1日のアクセス: 約1万PV

各クエリについて、
1. どのインデックスを張るべきか
2. 複合インデックスの場合、カラムの順序とその理由
3. インデックスのデメリット（書き込みの遅延、容量）

を教えてください。

ただし、あなたの提案が正しいかは私が EXPLAIN で確認します。
「EXPLAIN で何を確認すればよいか」も教えてください。
```

> ⚠️ **インデックスの提案は、必ず `EXPLAIN` で検証してください。**
> AIはデータの分布（値の偏り）を知りません。
> 「効くはず」のインデックスが、実際には使われないこともあります。

### 演習3（必須）─ わざと悪いSQLをレビューさせる

以下のSQLをAIにレビューさせ、**すべての問題を指摘できるか**確認してください。

```php
<?php
$keyword = $_GET["q"];
$sort = $_GET["sort"];
$sql = "SELECT p.*, COUNT(*) AS likes
        FROM posts p
        LEFT JOIN likes l ON l.post_id = p.id
        WHERE p.body LIKE '%{$keyword}%'
        GROUP BY p.id
        ORDER BY {$sort}";
$result = $pdo->query($sql);
```

**この中には、少なくとも4つの問題があります。**

<details>
<summary>問題の一覧（自分で探してからAIと比較）</summary>

1. **`{$keyword}` を文字列連結** → SQLインジェクション
2. **`{$sort}` を ORDER BY に直接** → SQLインジェクション（プレースホルダで守れない箇所）
3. **`LEFT JOIN + COUNT(*)`** → いいね0件の投稿も 1 になる（`COUNT(l.id)` にすべき）
4. **`SELECT p.*` と `GROUP BY p.id`** → MySQL 8.0 では `p.*` の他のカラムでエラーになりうる
5. **`LIKE '%...%'`** → 前方の % でインデックスが効かない + ワイルドカードのエスケープなし

**AIがこれらをすべて指摘できたか**、確認してください。
指摘できなかった項目があれば、それが「AIの守備範囲」の限界です。

</details>
