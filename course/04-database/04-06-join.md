## 📖 なぜ JOIN が必要か

4-5 で、テーブルを分割しました。**その結果、こうなります。**

```
posts                          users
┌────┬─────────┬──────────┐   ┌────┬──────────┬──────────────────┐
│ id │ user_id │ body     │   │ id │ name     │ email            │
├────┼─────────┼──────────┤   ├────┼──────────┼──────────────────┤
│ 1  │ 1       │ 投稿A    │   │ 1  │ 山田太郎 │ taro@example.com │
│ 2  │ NULL    │ 投稿B    │   │ 2  │ 佐藤花子 │ hana@example.com │
│ 3  │ 2       │ 投稿C    │   └────┴──────────┴──────────────────┘
└────┴─────────┴──────────┘
```

**「投稿一覧に、投稿者のメールアドレスを表示したい」** とき、
`posts` テーブルだけでは足りません。**2つのテーブルを繋ぐ必要があります。**

### ❌ やってはいけない方法（N+1問題）

```php
// ① 投稿を10件取得
$posts = $pdo->query("SELECT * FROM posts ORDER BY created_at DESC LIMIT 10")->fetchAll();

// ② 1件ずつユーザーを取得 ← ★ これが10回のクエリになる
foreach ($posts as &$post) {
    $stmt = $pdo->prepare("SELECT name, email FROM users WHERE id = ?");
    $stmt->execute([$post["user_id"]]);
    $post["user"] = $stmt->fetch();
}
```

**クエリの回数：1 + 10 = 11回。** これが **N+1問題**です。

| 投稿の表示件数 | クエリ回数 |
| --- | --- |
| 10件 | 11回 |
| 50件 | 51回 |
| 100件 | 101回 |

**1回のクエリが1msでも、100件なら100ms。** データベースとの通信往復が積み重なります。

### ✅ JOIN を使う

```sql
SELECT p.id, p.body, u.name, u.email
FROM posts p
INNER JOIN users u ON p.user_id = u.id
ORDER BY p.created_at DESC
LIMIT 10;
```

**クエリの回数：1回。** これが JOIN の価値です。

## ✍️ 手を動かす① ─ INNER JOIN（両方にあるものだけ）

```sql
SELECT p.id, u.name AS user_name, p.body
FROM posts p
INNER JOIN users u ON p.user_id = u.id
ORDER BY p.id
LIMIT 5;
```

### 結果

```
+----+-----------+--------------------------------------------+
| id | user_name | body                                       |
+----+-----------+--------------------------------------------+
| 1  | 山田太郎  | はじめまして。よろしくお願いします。       |
| 3  | 佐藤花子  | このサイト、使いやすいですね。             |
| 4  | 鈴木一郎  | 質問があります。\nどこに書けばいいですか？ |
| 6  | 田中美咲  | 週末のイベント、参加します！               |
| 7  | 山田太郎  | 私も参加します。                           |
+----+-----------+--------------------------------------------+
(5 rows)
```

> ⚠️ **id 2 と 5 がありません。** これらは `user_id` が NULL（ゲスト投稿）だからです。
>
> **`INNER JOIN` は「両方のテーブルに対応する行があるもの」だけを返します。**

### 構文を分解する

```sql
FROM posts p                        -- ① 基準となるテーブル（別名 p）
INNER JOIN users u                  -- ② 繋ぐテーブル（別名 u）
    ON p.user_id = u.id             -- ③ 繋ぐ条件
```

| 部分 | 意味 |
| --- | --- |
| `posts p` | `posts` テーブルに `p` という別名を付ける |
| `INNER JOIN users u` | `users` を `u` として繋ぐ |
| `ON p.user_id = u.id` | **`posts.user_id` と `users.id` が一致する行を対応させる** |

### 別名（エイリアス）を必ず付ける

```sql
-- ❌ どちらのテーブルの id なのか曖昧
SELECT id, name FROM posts INNER JOIN users ON posts.user_id = users.id;
--   Error: Column 'id' in field list is ambiguous

-- ❌ 毎回テーブル名を書くと長い
SELECT posts.id, users.name FROM posts INNER JOIN users ON posts.user_id = users.id;

-- ✅ 別名を使う
SELECT p.id, u.name FROM posts p INNER JOIN users u ON p.user_id = u.id;
```

> 💡 **別名は1〜2文字**にするのが慣習です（`posts` → `p`、`order_items` → `oi`）。
> ただし、テーブルが5つ以上になると意味が読めなくなるので、`post`, `user` のように
> 短い単語にすることもあります。**チーム内で揃えてください。**

### 同名カラムには別名を付ける

```sql
-- ❌ どちらも "name" なので、PHPで受け取ると片方が消える
SELECT p.name, u.name FROM posts p INNER JOIN users u ON p.user_id = u.id;

-- ✅ 別名を付ける
SELECT p.name AS post_name, u.name AS user_name
FROM posts p INNER JOIN users u ON p.user_id = u.id;
```

> ⚠️ **これは実際にハマります。**
> PHPで `$row["name"]` と書いたとき、**後に書いたほうの値**が入ります。
> JOINしたら、**重複するカラム名に必ず別名を付けてください。**

## ✍️ 手を動かす② ─ LEFT JOIN（左を全部残す）

```sql
SELECT p.id, p.name, u.email
FROM posts p
LEFT JOIN users u ON p.user_id = u.id
ORDER BY p.id
LIMIT 5;
```

### 結果

```
+----+------------+--------------------+
| id | name       | email              |
+----+------------+--------------------+
| 1  | 山田太郎   | taro@example.com   |
| 2  | 名無しさん | NULL               |
| 3  | 佐藤花子   | hanako@example.com |
| 4  | 鈴木一郎   | ichiro@example.com |
| 5  | 名無しさん | NULL               |
+----+------------+--------------------+
(5 rows)
```

**id 2 と 5 も返り、`email` が `NULL` になっています。**

> 🆘 **ここで詰まったら**（JOINで行が消える／増えすぎる／`ambiguous` エラー）
> - **行が消えた**：`INNER JOIN` は「両方にある行だけ」。相手がいない行も残したいなら `LEFT JOIN`（上の例）
> - **行が増えすぎた**：`ON` の結合条件が緩い（別々のキーで結ぶべき所を取り違えている）。1対多で「多」の件数だけ増えるのは正常
> - **`Column 'id' in field list is ambiguous`**：両方のテーブルに同じ列名があるのに、どちらか指定していない。`p.id` `u.id` のように**テーブル名（別名）を付ける**
> - **直らなければ、AIにこう聞く**（両テーブルの定義と、欲しい結果の例を貼る）：
>   「この JOIN が意図どおりの行を返しません。INNER と LEFT のどちらを使うべきか、ON の条件は正しいか教えてください」

### 図で理解する

```
INNER JOIN                      LEFT JOIN
                                (左＝FROM に書いたテーブル)

  posts    users                  posts    users
 ┌─────┐  ┌─────┐               ┌─────┐  ┌─────┐
 │     │  │     │               │█████│  │     │
 │  ███│██│███  │               │█████│██│███  │
 │     │  │     │               │█████│  │     │
 └─────┘  └─────┘               └─────┘  └─────┘
  ↑ 重なった部分だけ返る          ↑ 左は全部返る（右が無ければNULL）
```

### 使い分け

| やりたいこと | 使うもの |
| --- | --- |
| 会員の投稿だけ表示 | **`INNER JOIN`** |
| 全投稿を表示（ゲストも含む） | **`LEFT JOIN`** |
| 返信がある投稿だけ | `INNER JOIN` |
| 全投稿と、その返信数（0件も含む） | **`LEFT JOIN`** |

> 💡 **迷ったら `LEFT JOIN` を使ってください。**
> `INNER JOIN` だと、**気づかないうちにデータが消えます**。
> 「なぜか一覧に出ない投稿がある」というバグの原因の多くがこれです。

### JOIN の種類

| 種類 | 挙動 | MySQL |
| --- | --- | --- |
| `INNER JOIN` | 両方にあるものだけ | ✅ |
| `LEFT JOIN`（= `LEFT OUTER JOIN`） | 左を全部 | ✅ |
| `RIGHT JOIN` | 右を全部 | ✅（**使わない**） |
| `FULL OUTER JOIN` | 両方全部 | ❌ **MySQLにはない** |
| `CROSS JOIN` | 全組み合わせ | ✅（滅多に使わない） |

> 💡 **`RIGHT JOIN` は使わないでください。**
> `LEFT JOIN` でテーブルの順序を入れ替えれば同じことができます。
> **「左を全部残す」に統一したほうが、読むときに混乱しません。**

## ✍️ 手を動かす③ ─ 3つ以上のテーブルを繋ぐ

多対多（`posts` ←→ `post_tag` ←→ `tags`）を繋ぎます。

```sql
SELECT p.id, p.body, t.name AS tag
FROM posts p
INNER JOIN post_tag pt ON pt.post_id = p.id
INNER JOIN tags t      ON t.id = pt.tag_id
ORDER BY p.id, t.id;
```

### 結果

```
+----+--------------------------------------------+----------+
| id | body                                       | tag      |
+----+--------------------------------------------+----------+
| 1  | はじめまして。よろしくお願いします。       | 雑談     |
| 4  | 質問があります。\nどこに書けばいいですか？ | 質問     |
| 6  | 週末のイベント、参加します！               | 雑談     |
| 6  | 週末のイベント、参加します！               | お知らせ |
| 10 | 写真を投稿できる機能が欲しいです。         | 質問     |
| 10 | 写真を投稿できる機能が欲しいです。         | 要望     |
+----+--------------------------------------------+----------+
(6 rows)
```

> ⚠️ **投稿6と10が2回出ています。**
>
> タグが2つ付いているため、**行が増えます**。これは JOIN の正しい挙動です。
> 「投稿は6件」ではなく「投稿とタグの組み合わせが6件」です。
>
> **これを知らないと、`COUNT(*)` の結果がおかしくなります。**

### タグを1行にまとめる（GROUP_CONCAT）

```sql
SELECT
    p.id,
    p.body,
    GROUP_CONCAT(t.name ORDER BY t.id SEPARATOR ', ') AS tags
FROM posts p
LEFT JOIN post_tag pt ON pt.post_id = p.id
LEFT JOIN tags t      ON t.id = pt.tag_id
GROUP BY p.id, p.body
ORDER BY p.id
LIMIT 6;
```

```
+----+--------------------------------------------+----------------+
| id | body                                       | tags           |
+----+--------------------------------------------+----------------+
| 1  | はじめまして。よろしくお願いします。       | 雑談           |
| 2  | テスト投稿です。                           | NULL           |
| 3  | このサイト、使いやすいですね。             | NULL           |
| 4  | 質問があります。\nどこに書けばいいですか？ | 質問           |
| 5  | ↑ここでいいと思います                      | NULL           |
| 6  | 週末のイベント、参加します！               | 雑談, お知らせ |
+----+--------------------------------------------+----------------+
```

**投稿ごとに1行になり、タグがカンマ区切りでまとまりました。**

> ⚠️ **`GROUP_CONCAT` には長さの上限があります**（既定 1024バイト）。
> 超えると**黙って切り詰められます**。タグが大量にある場合は注意してください。
>
> ```sql
> SET SESSION group_concat_max_len = 10000;
> ```

> 💡 **`GROUP_CONCAT` は MySQL 専用です。** PostgreSQL では `string_agg`、
> SQLite では `group_concat`（区切り文字の指定方法が違う）です。

## ✍️ 手を動かす④ ─ JOIN と集計を組み合わせる

**最もよく使うパターンです。「一覧に件数を表示する」。**

### 返信数を表示する

```sql
SELECT
    p.id,
    p.name,
    p.body,
    COUNT(c.id) AS comment_count
FROM posts p
LEFT JOIN comments c ON c.post_id = p.id
GROUP BY p.id, p.name, p.body
ORDER BY p.id
LIMIT 6;
```

```
+----+------------+--------------------------------------------+---------------+
| id | name       | body                                       | comment_count |
+----+------------+--------------------------------------------+---------------+
| 1  | 山田太郎   | はじめまして。よろしくお願いします。       | 3             |
| 2  | 名無しさん | テスト投稿です。                           | 0             |
| 3  | 佐藤花子   | このサイト、使いやすいですね。             | 0             |
| 4  | 鈴木一郎   | 質問があります。\nどこに書けばいいですか？ | 2             |
| 5  | 名無しさん | ↑ここでいいと思います                      | 0             |
| 6  | 田中美咲   | 週末のイベント、参加します！               | 1             |
+----+------------+--------------------------------------------+---------------+
```

### ⚠️ `COUNT(*)` ではなく `COUNT(c.id)` を使う理由

```sql
-- ❌ 返信が0件でも 1 になる
SELECT p.id, COUNT(*) FROM posts p LEFT JOIN comments c ON c.post_id = p.id GROUP BY p.id;

-- ✅ 返信が0件なら 0 になる
SELECT p.id, COUNT(c.id) FROM posts p LEFT JOIN comments c ON c.post_id = p.id GROUP BY p.id;
```

**`LEFT JOIN` で相手がない行は、`c.id` が `NULL` になります。**
`COUNT(*)` は行数を数えるので 1、`COUNT(c.id)` は NULL を除くので 0 です。

> ⚠️ **これは実務で本当にハマります。**
> 「返信0件なのに1件と表示される」というバグの原因です。
> **`LEFT JOIN` + `COUNT` では、必ず結合先のカラムを数えてください。**

### HAVING で絞り込む

```sql
SELECT
    p.id,
    p.body,
    COUNT(c.id) AS comment_count
FROM posts p
INNER JOIN comments c ON c.post_id = p.id
GROUP BY p.id, p.body
HAVING COUNT(c.id) >= 2
ORDER BY comment_count DESC;
```

```
+----+--------------------------------------------+---------------+
| id | body                                       | comment_count |
+----+--------------------------------------------+---------------+
| 1  | はじめまして。よろしくお願いします。       | 3             |
| 4  | 質問があります。\nどこに書けばいいですか？ | 2             |
+----+--------------------------------------------+---------------+
(2 rows)
```

## ✍️ 手を動かす⑤ ─ 「〜がないもの」を探す

**これは実務で頻出しますが、書き方を知らないと詰まります。**

### LEFT JOIN + IS NULL

```sql
-- 返信が1件もない投稿
SELECT p.id, p.name, p.body
FROM posts p
LEFT JOIN comments c ON c.post_id = p.id
WHERE c.id IS NULL
ORDER BY p.id
LIMIT 5;
```

```
+----+------------+--------------------------------+
| id | name       | body                           |
+----+------------+--------------------------------+
| 2  | 名無しさん | テスト投稿です。               |
| 3  | 佐藤花子   | このサイト、使いやすいですね。 |
| 5  | 名無しさん | ↑ここでいいと思います          |
| 7  | 山田太郎   | 私も参加します。               |
| 8  | 高橋健     | よろしくお願いします 😊        |
+----+------------+--------------------------------+
(5 rows)
```

### 仕組み

```
① LEFT JOIN で、返信がない投稿も残す（c.* が NULL になる）
② WHERE c.id IS NULL で、「返信がなかった行」だけを抽出する
```

### 他の書き方

```sql
-- NOT EXISTS（意図が読みやすい。パフォーマンスも良い）
SELECT p.id, p.name, p.body
FROM posts p
WHERE NOT EXISTS (
    SELECT 1 FROM comments c WHERE c.post_id = p.id
);

-- NOT IN（★ NULL があると壊れる。使わない）
SELECT * FROM posts WHERE id NOT IN (SELECT post_id FROM comments);
```

> ⚠️ **`NOT IN` にサブクエリを使うのは危険です。**
>
> サブクエリの結果に **NULL が1つでも含まれると、全体が「該当なし」になります**。
>
> ```sql
> -- comments.post_id に NULL があると、何も返らない
> SELECT * FROM posts WHERE id NOT IN (SELECT post_id FROM comments);
> ```
>
> **`NOT EXISTS` か `LEFT JOIN + IS NULL` を使ってください。**

### `ON` と `WHERE` の違い（重要）

**`LEFT JOIN` では、条件を `ON` に書くか `WHERE` に書くかで結果が変わります。**

```sql
-- ① ON に書く：条件に合わない返信は「無かったこと」になるが、投稿は残る
SELECT p.id, COUNT(c.id) AS cnt
FROM posts p
LEFT JOIN comments c ON c.post_id = p.id AND c.name = '山田太郎'
GROUP BY p.id;
--   → 全投稿が返る。山田太郎の返信数が0でも行は残る

-- ② WHERE に書く：条件に合わない行が消える（LEFT JOIN の意味がなくなる）
SELECT p.id, COUNT(c.id) AS cnt
FROM posts p
LEFT JOIN comments c ON c.post_id = p.id
WHERE c.name = '山田太郎'
GROUP BY p.id;
--   → 山田太郎が返信した投稿だけが返る
```

> 💡 **覚え方**
> - **`ON`** = 「どう繋ぐか」の条件 → **左のテーブルの行は消えない**
> - **`WHERE`** = 「結合後に何を残すか」の条件 → **行が消える**
>
> `LEFT JOIN` で「右側のテーブルの条件」を書くときは、**`ON` に書くのが正解**です。
> `WHERE` に書くと、実質 `INNER JOIN` になります。

## ✍️ 手を動かす⑥ ─ サブクエリ

**クエリの中に別のクエリを書く方法です。**

### WHERE の中で使う

```sql
-- 返信を1件以上している人の投稿
SELECT * FROM posts
WHERE name IN (SELECT DISTINCT name FROM comments);

-- 平均より本文が長い投稿
SELECT id, name, CHAR_LENGTH(body) AS len
FROM posts
WHERE CHAR_LENGTH(body) > (SELECT AVG(CHAR_LENGTH(body)) FROM posts);
```

### SELECT の中で使う（相関サブクエリ）

```sql
SELECT
    p.id,
    p.body,
    (SELECT COUNT(*) FROM comments c WHERE c.post_id = p.id) AS comment_count
FROM posts p
ORDER BY p.id
LIMIT 5;
```

**`LEFT JOIN + GROUP BY` と同じ結果になります。**

| | JOIN + GROUP BY | 相関サブクエリ |
| --- | --- | --- |
| 読みやすさ | やや複雑 | **わかりやすい** |
| `GROUP BY` に全カラムを書く必要 | **ある**（面倒） | ない |
| 速度 | **一般に速い** | 行ごとに実行されるので遅くなりうる |

> 💡 **「1つの集計値を足すだけ」なら、相関サブクエリのほうが読みやすいです。**
> 件数が多い、集計が複数ある場合は JOIN のほうが速くなります。
> **`EXPLAIN` で確認して判断してください。**

### FROM の中で使う（派生テーブル）

```sql
-- 返信数ごとの投稿数
SELECT comment_count, COUNT(*) AS post_count
FROM (
    SELECT p.id, COUNT(c.id) AS comment_count
    FROM posts p
    LEFT JOIN comments c ON c.post_id = p.id
    GROUP BY p.id
) AS t
GROUP BY comment_count
ORDER BY comment_count;
```

```
+---------------+------------+
| comment_count | post_count |
+---------------+------------+
| 0             | 8          |
| 1             | 2          |
| 2             | 1          |
| 3             | 1          |
+---------------+------------+
(4 rows)
```

**「返信が0件の投稿が8件、1件の投稿が2件…」** と読みます。
合計 8+2+1+1 = 12 で、全投稿数と一致することを確認してください。

> ⚠️ **`FROM` のサブクエリには、必ず別名（`AS t`）が必要です。** 忘れるとエラーになります。

## ✍️ 手を動かす⑦ ─ 実践：掲示板の一覧クエリ

**第4部の総合演習で使う、本番のクエリです。**

```sql
SELECT
    p.id,
    p.name                                             AS post_name,
    p.body,
    p.created_at,
    p.user_id,
    u.name                                             AS user_name,
    COUNT(DISTINCT c.id)                               AS comment_count,
    GROUP_CONCAT(DISTINCT t.name ORDER BY t.id SEPARATOR ',') AS tags
FROM posts p
LEFT JOIN users    u  ON u.id = p.user_id
LEFT JOIN comments c  ON c.post_id = p.id
LEFT JOIN post_tag pt ON pt.post_id = p.id
LEFT JOIN tags     t  ON t.id = pt.tag_id
GROUP BY p.id, p.name, p.body, p.created_at, p.user_id, u.name
ORDER BY p.created_at DESC
LIMIT 10;
```

### ⚠️ `DISTINCT` が必要な理由

**`comments` と `post_tag` を両方 JOIN すると、行が掛け算されます。**

```
投稿1：返信3件 × タグ1個 = 3行
投稿6：返信1件 × タグ2個 = 2行
投稿10：返信1件 × タグ2個 = 2行
```

`COUNT(c.id)` だと、**タグの数だけ返信が重複して数えられます**。

| 書き方 | 投稿6の返信数 |
| --- | --- |
| `COUNT(c.id)` | **2**（タグ2個 × 返信1件）❌ |
| `COUNT(DISTINCT c.id)` | **1** ✅ |

> ⚠️ **これは「JOINの掛け算」という、非常に見つけにくいバグです。**
>
> **複数の1対多を同時に JOIN したら、必ず `DISTINCT` を疑ってください。**

### より安全な書き方：サブクエリで分ける

```sql
SELECT
    p.id,
    p.name AS post_name,
    p.body,
    p.created_at,
    u.name AS user_name,
    (SELECT COUNT(*) FROM comments c WHERE c.post_id = p.id) AS comment_count,
    (SELECT GROUP_CONCAT(t.name ORDER BY t.id SEPARATOR ',')
       FROM post_tag pt
       INNER JOIN tags t ON t.id = pt.tag_id
      WHERE pt.post_id = p.id) AS tags
FROM posts p
LEFT JOIN users u ON u.id = p.user_id
ORDER BY p.created_at DESC
LIMIT 10;
```

**`GROUP BY` が不要になり、掛け算の問題も起きません。**

> 💡 **10件程度の一覧なら、こちらのほうが安全で読みやすいです。**
> 「複数の1対多を集計するなら、サブクエリに分ける」を基本にしてください。

## ✍️ 手を動かす⑧ ─ N+1問題を実感する

**PHPでの実装は 4-7 で行いますが、考え方を先に押さえます。**

```
【N+1問題のあるコード】
  SELECT * FROM posts LIMIT 10                    ← 1回
  SELECT * FROM users WHERE id = 1                ← 1回目
  SELECT * FROM users WHERE id = 2                ← 2回目
  ...                                              ← 計10回
  合計 11回

【JOIN で解決】
  SELECT ... FROM posts LEFT JOIN users ...       ← 1回
  合計 1回

【IN でまとめる（JOINしづらい場合）】
  SELECT * FROM posts LIMIT 10                    ← 1回
  SELECT * FROM users WHERE id IN (1,2,3,4,5)     ← 1回
  合計 2回
```

### `IN` でまとめる方法

**「返信を全部取ってきて、PHPで振り分ける」**という方法です。

```sql
-- ① 投稿を取得
SELECT id, name, body FROM posts ORDER BY created_at DESC LIMIT 10;
--   → id が 12,11,10,9,8,7,6,5,4,3 だったとする

-- ② それらの返信を1回で取得
SELECT post_id, name, body FROM comments
WHERE post_id IN (12,11,10,9,8,7,6,5,4,3)
ORDER BY post_id, created_at;
```

PHPで `post_id` をキーにグループ化すれば、各投稿の返信が揃います。

> 💡 **これは Laravel の Eager Loading（`with()`）が内部でやっていることです。**
> 第5部（5-7）で「N+1問題」として再登場します。**いま仕組みを理解しておくと理解が速くなります。**

### どちらを使うか

| 状況 | 方法 |
| --- | --- |
| 1対1の関係（投稿→投稿者） | **`JOIN`** |
| 1対多で、件数だけ欲しい | **`JOIN` + `COUNT`** または相関サブクエリ |
| 1対多で、中身も全部欲しい | **`IN` でまとめて取得し、PHPで振り分け** |
| 多対多 | **`IN` でまとめる**（JOINすると掛け算になる） |

## ⚠️ つまずきポイントまとめ

| 症状 | 原因 | 対処 |
| --- | --- | --- |
| `Column 'id' is ambiguous` | どちらのテーブルか曖昧 | `p.id` のように修飾する |
| 一部の行が返らない | `INNER JOIN` で相手がない | `LEFT JOIN` にする |
| 行数が増える | 1対多を JOIN した | 正しい挙動。`GROUP BY` か `DISTINCT` |
| 0件なのに1件と表示される | `COUNT(*)` を使った | `COUNT(結合先のカラム)` |
| 件数が多すぎる | 複数の1対多を JOIN した | `COUNT(DISTINCT ...)` かサブクエリ |
| `LEFT JOIN` が効かない | 条件を `WHERE` に書いた | `ON` に書く |
| `NOT IN` で何も返らない | サブクエリに NULL が含まれる | `NOT EXISTS` を使う |
| `GROUP_CONCAT` が途中で切れる | 既定1024バイトの上限 | `group_concat_max_len` を広げる |
| `FROM` のサブクエリでエラー | 別名がない | `AS t` を付ける |
| JOIN したら急に遅くなった | 結合カラムにインデックスがない | 外部キーにインデックスを張る |

### JOIN が遅いときのチェック

```sql
EXPLAIN SELECT ... FROM posts p LEFT JOIN users u ON u.id = p.user_id ...;
```

| 確認すること | 良い状態 |
| --- | --- |
| `key` 列 | インデックス名が入っている（`NULL` はNG） |
| `type` 列 | `eq_ref` / `ref`（`ALL` はNG） |
| `rows` 列 | 小さい |
| `Extra` 列 | `Using index` が理想。`Using temporary` / `Using filesort` は遅い兆候 |

> 💡 **JOIN するカラムには、必ずインデックスを張ってください。**
> `posts.user_id` にインデックスがないと、投稿1件ごとに `users` を全件走査します。

### 演習2（必須）─ 間違いを見つける

```sql
-- ①
SELECT id, name FROM posts p INNER JOIN users u ON p.user_id = u.id;

-- ②
SELECT p.id, COUNT(*) AS comment_count
FROM posts p LEFT JOIN comments c ON c.post_id = p.id
GROUP BY p.id;

-- ③
SELECT p.id, p.body
FROM posts p
LEFT JOIN comments c ON c.post_id = p.id
WHERE c.name = '山田太郎';

-- ④
SELECT * FROM posts WHERE id NOT IN (SELECT post_id FROM comments);

-- ⑤
SELECT p.id, COUNT(c.id) AS comments, COUNT(pt.tag_id) AS tags
FROM posts p
LEFT JOIN comments c  ON c.post_id = p.id
LEFT JOIN post_tag pt ON pt.post_id = p.id
GROUP BY p.id;

-- ⑥
SELECT p.name, u.name FROM posts p INNER JOIN users u ON p.user_id = u.id;
```

<details>
<summary>答えを見る</summary>

① **`id` と `name` がどちらのテーブルか曖昧** → `Column 'id' in field list is ambiguous`
```sql
SELECT p.id, u.name FROM posts p INNER JOIN users u ON p.user_id = u.id;
```

② **`COUNT(*)` なので、返信0件の投稿も 1 になる**
```sql
SELECT p.id, COUNT(c.id) AS comment_count ...
```

③ **`LEFT JOIN` の条件を `WHERE` に書いているため、実質 `INNER JOIN` になっている**
（山田太郎が返信していない投稿が消える）
```sql
-- 「全投稿と、山田太郎の返信の有無」を出したいなら
LEFT JOIN comments c ON c.post_id = p.id AND c.name = '山田太郎'
```

④ **`NOT IN` + サブクエリは、NULL が含まれると何も返らない**
```sql
SELECT p.* FROM posts p
WHERE NOT EXISTS (SELECT 1 FROM comments c WHERE c.post_id = p.id);
```

⑤ **複数の1対多を JOIN しているため、行が掛け算されて両方の件数が膨らむ**
```sql
SELECT p.id,
       COUNT(DISTINCT c.id)     AS comments,
       COUNT(DISTINCT pt.tag_id) AS tags
FROM posts p
LEFT JOIN comments c  ON c.post_id = p.id
LEFT JOIN post_tag pt ON pt.post_id = p.id
GROUP BY p.id;
```

⑥ **カラム名が両方 `name` なので、PHPで受け取ると片方が消える**
```sql
SELECT p.name AS post_name, u.name AS user_name ...
```

</details>
